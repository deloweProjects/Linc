## 2. Part A — 🔴 THE APP STICKS ON USB LONG AFTER THE CABLE IS GONE

**Owner's report, and the highest-value item in this file:** the app keeps reporting a USB connection
long after the cable has been physically disconnected, so it never falls back to the wireless path that
is sitting there working.

**Diagnose before fixing.** `ConnectionSupervisor` ranks transports **USB > wireless ADB > Direct TLS**
with preemption (D-022). Establish which is true:
- (a) the supervisor never learns the USB transport died — `UsbWatcherService` / the adb device list is
  not reporting the removal, or the health loop's 15 s poll is not treating it as a drop; or
- (b) it learns, but the **ranking keeps it pinned** because a dead USB entry still outranks a live
  wireless one; or
- (c) the **adb server's own stale entries** are the source of truth and they persist —
  `192.168.137.119:38787 offline` in the owner's output is exactly that shape.

**Say which, with evidence, before changing anything.** If it is (c), the fix is the
disconnect-before-reconnect hygiene M13 already established — **an `offline` entry must never be
treated as a live transport.**

**Whatever the cause: a transport that has not answered must lose its rank.** Add a harness check over a
pure function — something like `RankTransports(candidates with liveness) → chosen` — proving a stale USB
entry loses to a live wireless one.

## 3. Part B — 🔴 `get-serialno` OVER TCP RETURNS `ip:port`, SO THE IDENTITY CHECK PROVES NOTHING

Live output: `get-serialno = 10.229.217.188:5555` and `identity ok: True`. **The check compared an
endpoint against an endpoint.** v18's whole "reachability is not identity" rule is currently hollow — the
same class of defect as M9b's harness that re-implemented the guard it was testing.

**Fix:** get the real serial with `adb -s <endpoint> shell getprop ro.serialno` and compare **that**
against `DeviceRegistry.PairedSerial`. Keep `get-state = device` as the liveness half.

**Negative proof:** point the check at a wrong serial → it must fail. A check that cannot fail is not a
check.

## 4. Part C — the Direct-TLS listener advertises the WRONG interfaces

Owner's log, while on the phone's hotspot:
`"Direct connection ready on <vpn-address>, 10.44.154.48 — waiting for the phone to find this PC"`

**`<vpn-address>` is the Radmin VPN and `10.44.154.48` is the stale LAN address.** The hotspot interface
(`10.229.217.12`) is **absent**. So the fallback path advertises addresses the phone cannot reach.

**Fix:** re-enumerate advertised addresses **on link change**, not once at startup, and **rank
virtual/VPN adapters last** — `hotspotprobe` already classifies them (`[virtual/VPN — ranked last]`).
**Reuse that classification; do not write a second copy of it.**
