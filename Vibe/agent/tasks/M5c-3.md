## 1. Why this session exists

M5c-2 shipped the v15 display feature with **the UI not connected to the view model**. Specifically,
in `DESKTOP/Linc.Desktop/Views/DevicePage.xaml`, inside the Tools card's "Display" section:

- the rotation `ComboBox` is `SelectedItem="{x:Bind DisplayControl.RotationMode, Mode=OneWay}"` with
  **no `SelectionChanged`**;
- the adaptive-brightness `ToggleSwitch` is `IsOn="{x:Bind DisplayControl.BrightnessAutoToggleOn,
  Mode=OneWay}"` with **no `Toggled`**;
- consequently `SetRotationCommand` and `SetBrightnessAutoCommand` are invoked **nowhere** in `Views/`.

So moving those two controls sends nothing to the phone. The build was clean and `tools/displaysim`
was 23/23 green, because the harness only tests the pure `DisplayPayload` helpers — a layer below the
bug. **That gap is itself part of what you must fix (section 4).**

There is a second, subtler defect. The brightness `Slider` has **both** a `OneWay` `Value` binding
**and** `ValueChanged="BrightnessSlider_ValueChanged"`. WinUI raises `ValueChanged` on **programmatic**
changes too, so every incoming `status` that carries `brightnessLevel` sets `Value`, fires the handler,
and sends a `display.brightness.set` **back to the phone** — an echo on every status poll.

**Do not redesign anything.** `DisplayPayload`, `DisplayControlViewModel`, the 250 ms debounce, the
three nullable status fields, `ProtocolConstants.Version = 15` and the existing `displaysim` checks
are all correct and stay exactly as they are. The view model's **private setters are deliberate** —
they stop a `status` seed from triggering a send at the VM layer. Keep them private.

## 2. The design you will implement — the "differs from known state" guard

All three controls both **display remote state** and **originate commands**. That is the shape that
causes echo loops. Use one uniform guard for all three, in the code-behind:

> **A control event sends a command only when the control's new value DIFFERS from the view model's
> current known value. If they are equal, the event was caused by a binding update (a seed from
> `status`), so return without sending.**

Do **not** add a `_suppressing` boolean flag for this. The comparison guard is stateless and has no
ordering fragility, which is why it is the chosen design here. Trace it once to convince yourself:

1. User picks "landscape" → `SelectionChanged` fires; combo = `"landscape"`, `VM.RotationMode` is
   still `"portrait"` → **differ → send.** The command then optimistically sets `RotationMode = "landscape"`.
2. Phone's next `status` says `"landscape"` → VM setter runs → `OneWay` binding pushes it to the
   combo → `SelectionChanged` fires again; combo = `"landscape"`, `VM.RotationMode = "landscape"` →
   **equal → return.** No echo.

```csharp
private void RotationCombo_SelectionChanged(object sender, SelectionChangedEventArgs e)
{
    if (sender is not ComboBox combo || combo.SelectedItem is not string mode)
    {
        return;
    }
    // Binding-driven update (a seed from the phone's status), not a user choice.
    if (mode == DisplayControl.RotationMode)
    {
        return;
    }
    DisplayControl.SetRotationCommand.Execute(mode);
}

private void BrightnessAutoToggle_Toggled(object sender, RoutedEventArgs e)
{
    if (sender is not ToggleSwitch toggle)
    {
        return;
    }
    if (toggle.IsOn == (DisplayControl.BrightnessAuto == true))
    {
        return;
    }
    DisplayControl.SetBrightnessAutoCommand.Execute(toggle.IsOn);
}
```

And **replace** the existing slider handler body with the guarded version:

```csharp
private void BrightnessSlider_ValueChanged(object sender, RangeBaseValueChangedEventArgs e)
{
    var level = (int)e.NewValue;
    // Programmatic update from a status seed — do not echo it back to the phone.
    if (level == DisplayControl.BrightnessLevel)
    {
        return;
    }
    DisplayControl.SetBrightnessLevelCommand.Execute(level);
}
```
