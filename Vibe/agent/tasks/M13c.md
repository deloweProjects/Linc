## 2. Self-arming (the cable disappears)

**The chicken-and-egg:** `adb tcpip` needs an existing ADB connection. Solved once, at setup, then never
again.

**2.1 The one-time grant, and it must NOT violate D-001.** The mechanism is
`adb shell pm grant app.linc.android android.permission.WRITE_SECURE_SETTINGS`, which needs a cable or
an existing ADB session **exactly once**.

**D-001 says users never touch ADB or a terminal — and they will not have to.** Linc's onboarding
(**M2b**) already attaches over ADB with a cable and injects the companion APK. **Add the grant to that
existing flow**, right after the install, so it happens invisibly inside something the user is already
doing. **Find the real install call site and extend it; do not build a second ADB path.** Report where
you put it.

- It must be **idempotent** and must **never fail onboarding** — if the grant fails, log it, continue,
  and let the feature degrade. A user who declines or whose OEM blocks it still gets everything else.
- Surface the resulting capability honestly in the UI (**disable, don't hide**, with a plain-language
  reason — CONTRIBUTING.md).

**2.2 Arming, phone side.** With the permission held:
`Settings.Global.putInt(contentResolver, "adb_wifi_enabled", 1)`.

TLS pairing state persists across reboots, so **an already-paired PC needs no QR and no interaction** —
it just connects. Boot → arm → discover own port (M13b §2.2) → verify (M13b §2.3) → announce.

**Guard it:** check the permission is actually held before writing, catch `SecurityException`, and
report `denied` rather than letting it escape. **Never toggle it off behind the user's back** — arming is
a user-visible state change to their device.

**2.3 Promotion to a fixed port — an optimisation, never the primary path.** Once the desktop has *any*
working ADB connection it may issue `adb tcpip 5555`; adbd rebinds to a stable port and later link-ups
need no announcement at all. **It does not survive reboot.** Layer it on top of the TLS path; if you
find yourself depending on 5555 being there, you have inverted the design.

## 3. The speculative race, and the health loop

**3.1 Race, do not wait politely.** On link-up, fire an optimistic connect at the best guess
(`peer-or-gateway:5555`) **and** race it against the authoritative announcement when it arrives; first
success wins, and the loser is cancelled cleanly. The speculative branch lands whenever adbd is in
legacy tcpip mode, which after one promotion is most of the time.

**Both branches must still go through the full verify** (`get-state` **and** `get-serialno`) — a race
that skips identity checking is worse than no race.

**3.2 Health loop.** Poll `adb devices` every 3–5 s. On anything other than `device`, issue
**`adb disconnect <endpoint>` before re-resolving** — the adb server caches stale endpoints and silently
refuses the replacement. **Backoff exponential from 250 ms, cap 15 s; reset on any successful verify and
on every `gen` increment** (a new link event means conditions genuinely changed, so try eagerly again).

**3.3 Keepalive as a side effect worth relying on.** Most Android builds kill the SoftAP after 5–10
minutes with no clients. **The app link counts as a client**, so a low-rate keepalive on the control
socket incidentally keeps the hotspot up. **Check whether Linc's existing 15 s ping already does this
(BRAIN: "desktop pings every 15 s of idle") — if it does, change nothing and say so.**

**3.4 Instrument each stage separately.** Log elapsed ms for: link-up → app link, port discovery,
announce, `adb connect`, verify. Target is ~150–300 ms total; **anything above ~1.5 s means something is
accidentally scanning, and per-stage timings are the only way to see which.**
