# PART A — a startup failure must never again be invisible

## A1. Why this comes first

M12 Part A spent a whole session making the connection layer incapable of failing silently. **The
startup path has exactly the same disease and it is worse**, because it happens before any logger
exists: an exception in `App.OnLaunched` on a machine with no debugger kills the process with no window,
no dialog and no log. That is precisely what the owner just experienced, and **it is why we cannot
currently diagnose it.**

**Fix the visibility first. Then the cause is trivially findable — by us and by every future beta
tester.** Do not skip to Part B because you think you have spotted the bug.

## A2. Decided design

**A2.1 A last-resort crash log, written next to the executable.** Subscribe to
`AppDomain.CurrentDomain.UnhandledException` **and** `TaskScheduler.UnobservedTaskException` **and**
WinUI's `Application.UnhandledException`, as the **first thing** `App`'s constructor does — before any
service is touched, before `OnLaunched`. On a crash, append timestamp + exception type + message +
stack to `linc-startup-error.log` **beside the exe** (not `%LOCALAPPDATA%`, which a confused tester will
never find).

**A2.2 Wrap `OnLaunched`'s body in a try/catch that surfaces the failure.** On exception: write the log
(A2.1) and show a plain-language **`MessageBox`** (Win32 `MessageBoxW` via P/Invoke — do **not** try to
show a WinUI dialog, the framework may be the thing that failed). Text names the log file's full path
and says what to send. Then exit cleanly rather than hanging.

**A2.3 The message must be plain language and actionable.** No stack trace in the dialog — that goes in
the file. Something a non-developer can act on: what failed, where the log is, what to do next.

**A2.4 This must not change behaviour when nothing goes wrong.** No visible difference on a healthy
launch, no startup delay, no extra window. The handlers are inert until something throws.

**A2.5 Never log secrets** — same rule M12 Part A enforced. An exception message may contain a path;
that is fine. It must not contain clipboard text, notification bodies or key material.

## A3. The work

1. **`App.xaml.cs`** — the three handlers, the `OnLaunched` wrapper, the P/Invoke `MessageBoxW`, the log
   writer. **Put the log-line formatting in a pure static** so the harness calls it.
2. **`tools/startupsim`** — new harness (conventions per `presencesim`/`packagesim`: numbered sections,
   `Check`/`CheckSub`, temp roots, exit 0/1, `FindRepoRoot` both CWDs). Cover: the pure formatter
   produces a line containing timestamp, type, message and stack; **crude source-text checks** that
   `App.xaml.cs` registers all three handlers and that they are registered **in the constructor, before**
   any service construction — ordering is the whole point and a future session must not be able to move
   them below the service wiring silently.

## A4. Part A acceptance

1. MSBuild x64 → 0 errors, no new warnings in files you touched.
2. `tools/startupsim` green, exit 0.
3. **Prove it works, on this machine:** temporarily throw early in `OnLaunched`, run the built exe,
   **paste the generated `linc-startup-error.log` contents**, confirm the dialog appeared, then remove
   the throw and rebuild. This is a real end-to-end proof, not a harness check — do it.
4. **One negative proof against a PRODUCTION file:** move a handler registration below service

# PART B — find and fix the actual cause

## B1. What we know

- The owner copied `DESKTOP/Linc.Desktop/bin/x64/Release/net8.0-windows10.0.19041.0/win-x64/publish/`
  to a second PC. **No window, no error.**
- `WindowsAppSDKSelfContained=true`, `WindowsPackageType=None`, `SelfContained=true` are all already set.
- **The owner is being asked for the Windows Event Viewer entry and the second PC's Windows version.**
  If those are in your prompt, they are the strongest evidence you have — **start there.**

## B2. Hypotheses, ranked. Verify each; do not assume.

**B2.1 The Visual C++ Redistributable is missing.** Self-contained bundles .NET and the Windows App SDK
but **not** the VC++ runtime. A clean Windows install may lack it, and the failure mode is exactly this:
process dies instantly, no managed exception, nothing in the app's own logs. **Check which native DLLs
the publish output actually depends on** (`dumpbin /dependents`, or read the publish folder for
`msvcp140*.dll` / `vcruntime140*.dll`). If they are absent from the output, that is very likely the
answer — either bundle them or detect and tell the user.

**B2.2 The target Windows version is below 10.0.19041.** `TargetFramework` demands it. If the second PC
is older, nothing will run and no code change fixes it — **report it as an environment limit** and
document the minimum in the packaging output.

**B2.3 The wrong folder was copied.** The parent `Release/net8.0-windows10.0.19041.0/` directory is
**not** self-contained and would fail identically. **Confirm the publish folder is genuinely standalone**
by listing the runtime files that must be present (`coreclr.dll`, `hostfxr.dll`,
`Microsoft.WindowsAppRuntime.Bootstrap.dll` or its self-contained equivalents). If they are missing from
`publish/`, the profile is not doing what M12's report claimed.

**B2.4 A Content item resolves to an author-machine path at runtime.** M12 found no absolute paths in
shipped `.cs`, but **verify the bundled scrcpy and `companion.apk` actually land in `publish/`** — M12
verified them at their *source* paths, not in the published output. A missing asset that something
dereferences during startup would produce exactly this.

## B3. The work

Fix what you find. **If the cause is environmental (B2.2) rather than a code defect, say so plainly and
make the app detect and explain it** rather than pretending a code change fixed it. If you cannot
reproduce the failure at all on this machine, **say that** — Part A's crash log will capture it on the
owner's next attempt, and that is a legitimate outcome for this session.

**Extend `tools/packagesim`** with whatever the finding makes checkable — at minimum, that every payload
M12 verified at its source path is **also present in the publish output**, since that gap is what let a
broken package ship as green.

## B4. Part B acceptance

1. MSBuild x64 → 0 errors. Release publish re-run; **list the publish folder's top level and the
   payload paths** (scrcpy bundle, adb, `companion.apk`, assets) **as they exist in the output.**
2. `packagesim` green, exit 0, with the new output-side checks.
3. **One negative proof against a PRODUCTION file or the profile:** break whatever the new check guards
   → it fails → restore → green.
4. Full regression: `presencesim`, `startupsim`, `mirrorsettingssim`, `applaunchsim`, `appssim`,
   `homelayoutsim`, `displaysim`, `homecachesim`, `storesim`, `synccachesim`, `outboxsim`,
   `apkinstallsim`, `desktopsim` (honest either way) all green.
