# PART A — install an APK on the phone, from the PC

## A2. Decided design

**A2.1 This part legitimately uses ADB, and it is not a D-001 violation.** Installing a package is an
ADB capability with no protocol equivalent — the companion app cannot install another APK. **M2b already
does exactly this** to inject the companion app. **Reuse `PhoneSetupService`'s existing install
primitive. Do not write a second install path**, and do not "improve" the existing one.

**A2.2 Entry point: an "Install app" row in the Device page's Tools card**, beside the existing blocks.
File picker filtered to `.apk`. Follow the card's existing conventions; **do not restyle the page.**

**A2.3 Validate before touching the phone**, each failure its own plain-language message: file missing,
extension not `.apk`, zero bytes, no device connected. **Never show raw adb output** — D-009's shell box
is the only place raw output is allowed and this is not it.

**A2.4 Staged, honest progress:** `Validating` → `Copying to phone` → `Installing` → done or failed.
The UI must never sit on a frozen "Installing…" with no way to tell whether it died. **Disable the
button while a run is in flight** (one install at a time) and re-enable it in a `finally`.

**A2.5 Translate failures; never echo them.** Put the mapping in a **pure static**
`TranslateInstallFailure(string raw)` so the harness calls it directly. Minimum mappings:

| adb substring | user text |
|---|---|
| `INSTALL_FAILED_ALREADY_EXISTS` | "That app is already installed." |
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | "Not enough space on the phone." |
| `INSTALL_FAILED_INVALID_APK`, `INSTALL_PARSE_FAILED` | "That file isn't a valid Android app." |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, `SIGNATURE` | "A different version is already installed. Uninstall it first." |
| `INSTALL_FAILED_USER_RESTRICTED` | "The phone refused the install. Check it for a prompt." |
| anything else | "Install failed. The phone rejected the app." |

**Log the raw string; never surface it.**

**A2.6 Warn that the phone may prompt**, one line before starting: "Check your phone — it may ask you to
allow the install."

**A2.7 Never block the UI thread, never throw into it.** Fire-and-forget with a catch-all, same stance
as M9.

# PART B — the share sheet accepts files, and Share moves into Home

## B1. What is actually there (verified by the planner — confirm it yourself per §0.1)

`ShareReceiverActivity.kt` **already exists** (44 lines) and the manifest already registers it — but its
intent-filter is:

```xml
<action android:name="android.intent.action.SEND" />
<data android:mimeType="text/plain" />
```

**`text/plain` only.** It accepts shared *text*, not files, and not multi-select. That is the gap.
`Screen.kt` still lists `Share` as a bottom-nav destination.

## B2. Decided design

**B2.1 Accept files of any type, single and multiple.** Add to the manifest filter: `mimeType="*/*"` on
the existing `SEND` filter, plus a second filter for `ACTION_SEND_MULTIPLE` with `*/*`. **Keep the
`text/plain` behaviour working** — text sharing already ships and must not regress.

**B2.2 Read the payload correctly.** Single: `Intent.EXTRA_STREAM` as a `Uri`. Multiple:
`EXTRA_STREAM` as `ArrayList<Uri>`. Resolve display name and size through `ContentResolver` +
`OpenableColumns` — **never assume a file path**; a `content://` Uri frequently has none.

**B2.2a Copy into app storage before sending.** The sending grant on a `content://` Uri can be revoked
the moment the activity finishes. Copy each item into the app's cache dir first, then send from there,
then delete the copy once sent. **`OutgoingActions` already copies to an outbox for the picked-file
path — reuse that mechanism rather than writing a second one.**

**B2.3 Reuse `share.item kind:file` exactly as it is (v10, D-024). No protocol work.** Multiple files
are sent as **N sequential `share.item` messages, in the order the user selected them** — not a new
batch message.

**B2.4 Bound it.** Refuse any single item over **100 MB**, and any selection totalling over **250 MB**,
with a plain-language toast naming the limit. Put the limit check in a **pure function** so the unit
tests call it. Rationale: the bulk channel has no chunk-resume, so a huge transfer that dies mid-way
wastes everything — better to refuse clearly than fail late.

**B2.5 Not connected = refuse politely, do not queue.** Toast: "Linc isn't connected to your PC right
now." **A phone-side offline queue is explicitly out of scope** — M9c's outbox is desktop-side only, and
building a second queue on the phone is a milestone of its own.

**B2.6 The activity stays invisible.** It is `Theme.NoDisplay` and `excludeFromRecents` — keep both.
Feedback is a toast; it must **never** open the app UI. Finish the activity promptly; do not hold it
open for the duration of a large transfer — hand off to the service and finish.

**B2.7 Remove `Share` from the bottom nav and put it in Home.** Delete the `Share` entry from
`Screen.kt`'s enum, and move `ShareScreen`'s content into `HomeScreen` as its **own section**, following
whatever section pattern `HomeScreen.kt` already uses. **Home must scroll** — a new section on a screen
with no scroll host is the exact failure that cost the desktop a milestone (M5a; see `BRAIN.md`). If
`HomeScreen` is not already scrollable, make it so as part of this.

**B2.8 Do not delete `ShareScreen.kt` wholesale.** Move its composables into the Home section so the
history is a move, not a rewrite. If the file ends up empty, then remove it.

**B2.9 Never log file names or contents.** Log that a share happened and the item count.
