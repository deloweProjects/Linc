## 1. Why this task exists

**The owner has had to carry a build to a second PC three times and is out of patience with it.** They
are right to be. Every defect those trips found was the same shape: **the dev machine silently supplied
something the package did not.**

- M12b — `Linc.Desktop.pri` was never copied into `publish/`.
- M12c — `ToolLocator.FindAdb()` never looked in Linc's own bundle; the dev machine's Android SDK adb
  covered for it for the entire life of the project.
- M12c — all three dev-tree fallbacks used five `..` where six are needed, resolving to a path that has
  never existed; the `PATH`/winget scans below covered for it.

**Two of those three were environment-lending, and both are reproducible on this machine** by launching
the publish output with the lending switched off. That is what Part A builds. **The goal is that a second
PC becomes a rare final sign-off, not a per-milestone chore.**

**Be honest about the limit:** a machine-wide install (the VC++ redistributable, the .NET desktop
runtime, the WindowsAppSDK) cannot be hidden with an environment variable. Those stay second-PC
territory — but they are already covered by shipping the runtime app-local and by M12c's `dumpbin` sweep,
and they change far less often than our own code does. **Do not claim Part A replaces the second PC.
Claim what it actually covers.**

# PART A — `tools/cleanroomsim`

A new plain `net8.0` console following the existing harnesses' shape. It has **two independent halves**;
build both and keep them clearly separated in the output, because they prove different things.

## A1. Half one — the deterministic half: the real lookup functions, environment sanitised

This is the half that would have caught M12c, and it needs no process launch.

1. Build a fixture directory laid out like a publish tree — `<tmp>/SCRCPY/Linc.scrcpy/bin/` containing
   stub `adb.exe`, `scrcpy.exe`, `scrcpy-server`, `linc.ico`. **`packagesim` check 7 already does exactly
   this for adb; read it and reuse its approach rather than inventing a second one.**
2. Sanitise the environment **for the current process** around the calls:
   - `PATH` → `C:\Windows\system32;C:\Windows` only.
   - `ANDROID_HOME` and `ANDROID_SDK_ROOT` → removed.
   - `LOCALAPPDATA` → a throwaway temp directory (this is what hides `%LOCALAPPDATA%\Android\Sdk`).
   - **Restore every one of them in a `finally`.** A harness that leaves the process environment
     modified is a footgun of exactly the D-057 family.
3. Call the **real** `ToolLocator.FindAdb()`, `FindScrcpy()` and `FindScrcpyIcon()` against the fixture
   and assert each resolves to the **exact** bundled path — not merely non-null.
   **`FindAdb` returning a real SDK adb instead of the bundle is the M12c bug, and M12d's negative proof
   showed it fails by silently falling through, not by erroring.** Assert the full path.
4. Assert the same three calls **fail cleanly** (return null / a documented sentinel — read the code, do
   not assume) when the fixture's `bin/` is empty. A lookup that cannot fail proves nothing.

## A2. Half two — the launch half: does the published app survive with no help from this machine?

This is the half that would have caught M12b's missing `.pri`.

1. **Require a publish output. If `publish/` does not exist, SKIP with a loud message and a distinct exit
   path — never pass.** This is `packagesim`'s established rule and it exists because a harness that
   checks nothing and prints green is worse than no harness.
2. **CHECK FOR A RUNNING `Linc.Desktop` FIRST.** The app is single-instance via a
   `Local/LincDesktopSingleInstance` mutex — if the owner's real Linc is running, the child will exit
   immediately and you will measure the mutex, not the package. **If one is running, SKIP with a message
   telling the reader to close Linc and re-run.** Do not `Stop-Process` the owner's app.
3. Launch `publish/Linc.Desktop.exe` as a child with the sanitised environment from A1.2 — in particular
   with `LOCALAPPDATA` pointed at a throwaway temp root, so **the child writes its `settings.json`,
   `linc.db`, `cache/` and `logs/` into the temp root and cannot touch the owner's real store.** State
   this in a comment as the D-057 rule applied to a whole process.
4. Wait a fixed settle period (5 s is enough; do not tune it by feel), then assert:
   - the process is **still alive** — a startup failure kills it;
   - **no crash log was written** — resolve the filename from `Services/StartupCrashLogger.cs`, do not
     guess it, and check both beside the exe and under the redirected root;
   - the app's own log under the **redirected** root exists and names a resolved adb path **inside the
     bundle**. If the log does not record which adb it resolved, say so and assert what you can — **do
     not add logging to production code in this task** and do not pretend the check is stronger than it is.
5. **`Kill()` the child. Do not wait for it to exit.** `CloseMainWindow` hides it to the tray and it will
   never exit — an agent waiting on it will wait forever and conclude it hung. This is in BRAIN.
6. Delete the temp root in a `finally`.

# PART B — the `PRI249` warning, and `.pri` insurance

Re-read this file from the top, then continue.

## B1. What is known

M12d's fresh publish introduced:

```
PRI249: 0xdef00520 - Invalid qualifier: 0-0
```

The agent diagnosed it as the WinUI resource indexer (`makepri.exe`) scanning every project-wide
`Content` item — now including the scrcpy payload — and treating the **`.` in the folder name
`Linc.scrcpy`** as a resource qualifier delimiter. **It was absent before only because the stale glob
matched zero files.** It correctly refused to work around it unasked.

**Verified by the planner and not in doubt:** the publish output is **correct despite the warning** —
104 files in `publish/SCRCPY/Linc.scrcpy/bin/` including `adb.exe`, `scrcpy.exe` and `scrcpy-server`,
plus `Linc.Desktop.pri` present at the publish root and the app-local VC++ runtime. So this is **noise,
not breakage.**

**But noise is not harmless here:** `Linc.Desktop.pri` going missing is precisely the M12b defect that
killed the app on the second PC, and we now have the resource indexer emitting warnings. That earns one
cheap insurance check (B3).

## B2. The work — and the explicit permission to give up

**Goal:** the scrcpy payload is still copied to `publish/` (all 104 files) but is **not offered to the
resource indexer as a resource candidate**, so `PRI249` stops.

**PLANNER'S HYPOTHESIS — I HAVE NOT TESTED ANY OF THESE. VERIFY BEFORE IMPLEMENTING.** Plausible levers,
in the order I would try them:

1. Remove the payload from whatever item group the WinUI targets feed to `makepri.exe`, while keeping the
   copy-to-output behaviour — read the WindowsAppSDK targets to find the actual item name rather than
   guessing at metadata.
2. Carry the payload as `None` with `CopyToOutputDirectory` / a publish item instead of `Content`, if
   that keeps it out of indexing and still lands all 104 files.
3. A `priconfig` exclusion for that path.

**THE NAME `Linc.scrcpy` IS THE OWNER'S AND IS FINAL. Renaming the folder is NOT an option and is not a
solution to consider.**

**If none of these works cleanly in a reasonable effort, STOP AND SAY SO.** Leaving a cosmetic warning in
place is an acceptable outcome; a fragile build hack to silence it is not. **Report what you tried and
what it did.** Do not burn the session on this — Part A is the valuable half.
