## 2. PART A — one design language, both apps

**A1 — Decide the system once, write it down, then apply it.** Put the decisions at the top of your
report as a short table: the tonal roles, the spacing scale, the corner radii, the type scale, the
one elevation-or-outline choice, and the motion durations. **Both apps use the same table.** A user
moving from the phone to the PC should feel one product.

**A2 — Android.** All six screens: `HomeScreen`, `ToolsScreen`, `SettingsScreen`, `StatusScreen`,
`LogsScreen`, `OnboardingScreen`. Real top app bars, one card treatment, the M3 type scale (no
hand-set font sizes left), 48 dp minimum touch targets, consistent list/row rhythm.
**If `Vibe/agent/tasks/M17-CODE.md` exists, its `Dimens` / `LincCard` / `LincScreen` / `LincEmpty`
are the starting point** — extend them rather than forking a second system.

**A3 — Windows.** `HomePage`, `DevicePage`, `SettingsPage`, `SyncPage`, `FilesPage`, `LogsPage`,
`DetailsPage`, `OnboardingView`. The same rhythm: one `ExpressiveCard` treatment, consistent header
sizes (M5a left "Tools"/"Screen mirroring"/"Screen" all rendering at the same weight — fix that
class of thing), aligned control heights, real spacing tokens instead of scattered margins.
**Both themes must be checked** — light and dark.

**A4 — Fill the gaps.** These are what make it feel unfinished:
- **Empty states** — icon plus one sentence, never a bare label, on every list and pane.
- **Loading states** — anything that can take >300 ms shows progress, not a blank.
- **Error states** — plain language, an action where one exists, and never raw adb/scrcpy text.
- **Focus and hover** — visible keyboard focus on the desktop; tab order that follows the layout.
- **Long text and small windows** — nothing clipped, nothing overlapping, at the smallest sensible
  window size and in landscape on the phone.

## 3. PART B — dynamic colour, with the neutral default underneath

The plumbing exists: the phone sends its wallpaper (M15b made it sharp), `ThemeSyncService` already
derives a dominant colour and washes it into the surface and the Home scrim.

**B1 — Make it a real, deliberate feature rather than a side effect.** A setting on the desktop —
**"Use my phone's colours"**, default **ON** where the data exists — that derives the M3 tonal roles
from the wallpaper's dominant colour and falls back **cleanly and completely** to M14's neutral
black-and-white ramp when: the phone is disconnected, no wallpaper is available, or the setting is
off. **The fallback is not a special case to bolt on — it is the base state the app already ships.**

**B2 — Android's side.** The phone already uses `dynamicLight/DarkColorScheme` on API 31+ (D-011).
Keep that; make the **fixed** scheme (API 30 and the not-dynamic path) match the desktop's neutral
ramp exactly, so the two apps agree when neither has colour to work with.

**B3 — Contrast is not optional.** Whatever the wallpaper is, body text must clear **4.5:1** and
large text/icons **3:1**, in both themes. **Clamp the derived tones to guarantee it** — a dark
wallpaper must not produce grey-on-grey. **Report the clamping rule and the worst-case ratio you
measured.** This is the one place where "it looked fine on my wallpaper" is not evidence.

**B4 — No flicker.** A palette change mid-session must not flash white, restart a view model, or drop
the wallpaper for a frame. Say how you satisfied that.

**`prod/` must be gitignored** (it is build output, not source) — add the ignore rule and say so.
