## 1. PART A — the one-phone limit must be stated in the UI, before the user is confused

**Owner, verbatim, after hand-testing M15a:** *"I forgot I had to disconnect the Pixel. It's not
auto, so you need to let the user know — cancel, or disconnect one, connect and add another."*

M15a made the limit **reported** (`DeviceAdmission.DecideDeviceSwitch` + a message). It is still not
**visible before the fact**. Fix that:

**A1 — A choice, not a notice.** When a second phone becomes available while one is connected, the
confirmation card must offer exactly two actions, in plain language:
- **"Disconnect <current> and connect <new>"** (calls the existing `ConnectUsbManualAsync` path,
  which already tears the first link down first — verify that before relying on it)
- **"Cancel"** (dismisses; do not ask again for that serial until it is unplugged and replugged)

Reuse `DecideDeviceSwitch`'s sentence as the card's body. **No new decision logic** — if the pure
static already returns what you need, use it and say so.

**A2 — State it before the collision too.** Wherever a user can add/pair a phone (Devices page `+`,
Settings › Devices, the onboarding entry point), show one short standing line while a phone is
connected: **"Linc connects to one phone at a time. Adding another will disconnect <current>."**
Static text, no new state machine.

**A3 — Harness it.** Extend `hotspotsim`'s M15a section (or the nearest fitting harness — say which):
assert the card exposes both actions and that Cancel leaves the current link untouched. Pure statics
where possible; a crude source-text check on the XAML where not.

## 2. PART B — USB removal should be noticed in ~3 s, not 19

**Owner's measured numbers, real hardware:** cable out → **19 s** to notice; then **~1 s** to attach
USB on plug-in; **20 s** total to fall back to wireless. He wants the 19 s down.

M15a established detection is the health loop: first failed probe lands 0–15 s after death, then two
3 s confirms → **6–21 s**. That matches the 19 s exactly. **Do not lower `HealthInterval`** — it
costs battery and churn, and it is not the cheapest signal available.

**PLANNER'S HYPOTHESIS — verify before implementing.** `UsbWatcherService` **already polls
`adb devices` every 3 s** (`PollInterval`, master-read). When the live transport is `AdbUsb` and that
serial **disappears from the list** (or turns `offline`), that is a positive death signal ~15 s
cheaper than waiting for a probe to time out. **Nothing consumes it today** — the watcher only ever
raises "seen" and (since M15a) "unusable".

**B1 —** Confirm the poll really enumerates the live USB device and that a pulled cable removes it
from `adb devices` promptly. If adb keeps a stale entry (M13f saw this class), **say so and stop** —
report what the poll actually returns rather than shipping a fix built on a guess.

**B2 —** If confirmed: raise a `UsbDeviceGone(serial)` event; the supervisor treats it as an
immediate drop **only when the live transport is `AdbUsb` and the serial matches** — then run the
existing `OnLinkDropped()` path (which M15a already made trigger recovery). **Do not bypass the
health loop for any other transport**; a wireless link's absence from `adb devices` means nothing.

**B3 — Guard against a false drop.** One missing poll must not kill a healthy link. Require the
serial absent on **two consecutive polls** (~6 s worst case, still 3× better than today), or a single
`offline` reading plus one confirm. State which you chose and why.

**B4 —** Log the new path's timing the same way M15a logs detection, so the next cable pull is
measurable. **Report the expected best/worst case in seconds.**
