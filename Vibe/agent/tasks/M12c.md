# PART A — find the adb we already ship (this is the blocker; do it first)

## A1. The bug (planner-verified, read the file and confirm)

`Services/ToolLocator.cs` → `FindAdb()` searches exactly three candidates:

```csharp
Path.Combine(AppContext.BaseDirectory, "adb", "adb.exe"),                    // folder never created
Path.Combine(Environment.GetEnvironmentVariable("ANDROID_HOME") ?? "", "platform-tools", "adb.exe"),
Path.Combine(..., "Android", "Sdk", "platform-tools", "adb.exe"),            // %LOCALAPPDATA%
```

**None is the bundled location.** Two of the three are the author's Android SDK, which is why this has
worked on the dev machine for the entire life of the project and failed the first time it met a clean
one. Note that `FindScrcpy()` in the same file **does** resolve `SCRCPY/Custom/bin/` correctly — the
pattern to copy is ten lines below the bug.

## A2. Decided design

**A2.1 The bundled adb is the FIRST candidate, not a fallback.**

```csharp
Path.Combine(AppContext.BaseDirectory, "SCRCPY", "Custom", "bin", "adb.exe"),
```

placed **ahead** of every existing candidate. **Rationale, and it is not just about clean machines:**
the bundled `adb.exe` is the one matched to the bundled `scrcpy-server`. Preferring a random
system-installed adb of unknown version is a real correctness risk, not merely a packaging one. **Bundled
first makes behaviour deterministic on every machine.**

**A2.2 Keep the existing fallbacks, in their current order, after it.** A dev machine with no bundle
must still work. **Do not delete a candidate.**

**A2.3 Add the dev-tree candidate too**, mirroring what `FindScrcpy()` already does at line ~30 — the
`Path.GetFullPath(Path.Combine(BaseDirectory, "..", "..", "..", "..", "..", "SCRCPY", "Custom", "bin",
"adb.exe"))` shape — so a Debug build from `bin/x64/Debug/...` finds the repo's bundle rather than
silently falling through to the SDK. **Verify the depth is right by testing it, don't copy the count
blindly.**

**A2.4 The error message must say where it looked.** `Services/AdbServerHost.cs` currently says *"Linc
couldn't find its ADB engine on this PC. Reinstall Linc, or install …"*. That gave the owner nothing to
act on. It must name the expected bundled path, so the next person can see in one glance whether the
file is missing or the lookup is wrong. Plain language, no stack trace, no raw output.

**A2.5 Make the same audit for every other tool this app locates.** `FindScrcpy`, the icon lookup, and
anything else in `ToolLocator`. **Report whether each resolves from the bundle on a published layout**
— if another one has the same dev-machine dependency, fix it the same way and say so. This bug class is
almost certainly not unique.

# PART B — bundle the VC++ runtime DLLs app-local

## B1. The evidence is genuinely mixed, and the owner has decided

M12b ran `dumpbin /dependents` across all 647 published files and found **nothing importing
`msvcp140.dll` or `vcruntime140.dll`** — concluding the VC++ redist was not required. That is good
evidence and I am not dismissing it.

**But** the owner's second PC only launched after installing the VC++ redist **and** taking the `.pri`
fix — two changes at once, so neither is cleanly attributable. And the owner has asked directly for the
DLLs to ship with the app.

**Decision: ship them.** They cost ~1.5 MB against a 25 MB APK already in the bundle, they remove a
whole class of "works on my machine", and a beta tester should never be told to go install a
prerequisite. **If M12b's dumpbin analysis is right, this is harmless insurance. If it is wrong, it
fixes a real failure.** Either way the owner stops chasing it.

## B2. Decided design

**B2.1 Copy from the installed VS redist at publish time; do NOT vendor into the repo.** Adding
Microsoft binaries to source control is a licensing and hygiene problem this project does not need.
Source directory shape:
`C:\Program Files\Microsoft Visual Studio\18\Community\VC\Redist\MSVC\<version>\x64\Microsoft.VC143.CRT\`
— **locate it; do not hardcode the `<version>` folder.** If the toolset folder name differs, find it.

**B2.2 Which DLLs:** `msvcp140.dll`, `vcruntime140.dll`, `vcruntime140_1.dll`, plus `msvcp140_1.dll` and
`msvcp140_2.dll` if present in the redist folder. Copy to the **publish root**, beside `Linc.Desktop.exe`.
Do not overwrite `vcruntime140_cor3.dll` — that is .NET's own and is already correct.

**B2.3 Wire it into the publish, not a manual step.** Same mechanism M12b used for the `.pri` — a target
in `Beta.pubxml` that adds them to `ResolvedFileToPublish`. **Every publish must carry them.**

**B2.4 Fail the publish loudly if the redist source cannot be found**, with a plain-language message
naming the directory it looked in. **A silent publish that produces a broken folder is the exact failure
this whole milestone exists to eliminate** — and it has now happened twice.

**B2.5 Extend `tools/packagesim`** to assert all of them exist **in the publish output**. If the publish
folder is absent when the harness runs, that is a **skip with a clear message, never a pass.**

## B3. Part B acceptance

1. Publish re-run; **list the VC++ DLLs in the output**, proving they are there.
2. `packagesim` green including the new checks.
3. **Two negative proofs:** delete one VC++ DLL from the publish output → the check fails → re-publish →
   green. And point the redist source at a non-existent directory → the publish fails with the
   plain-language message → restore → green.
4. Full regression: `presencesim`, `startupsim`, `mirrorsettingssim`, `applaunchsim`, `appssim`,
   `homelayoutsim`, `displaysim`, `homecachesim`, `storesim`, `synccachesim`, `outboxsim`,
   `apkinstallsim`, `desktopsim` all green.
