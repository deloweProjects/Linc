# PART A — presence: say what is actually happening, and never fail silently

## A1. Why this part exists

The whole product hangs off `ConnectionSupervisor`'s state machine (NoDevice / Searching / Connecting /
Connected / Paused). When it works the user never thinks about it. **When it does not, the user is left
guessing** — and this project's own history says the failure is usually invisible rather than loud:
BRAIN's standing rule is *"a silent catch is a bug factory; if a path can fail and nobody is awaiting
it, it must log."*

The owner's recent phone session found four defects that every harness had passed, **three of them
silent** — a store that returned empty with no log, a cache read that never fired, notifications
dropped without a warning. **Part A is about making the connection layer incapable of that.**

## A2. Decided design

**A2.1 Audit every catch block in the connection path and classify it.** Files: `ConnectionSupervisor`,
`ConnectionManager`, `CompanionClient`, `DiscoveryService`, `UsbWatcherService`, `BlePresenceService`.
For each `catch`, decide which it is:

- **Expected and routine** (a poll that found nothing, a race on shutdown) → leave it, but add a
  one-line comment saying why it is silent. A silent catch with a stated reason is fine; an unexplained
  one is not.
- **Unexpected** → must `log`. Level `Warn` for recoverable, `Error` for a state the user will notice.
- **Swallowing a user-visible failure** → must log **and** surface a plain-language message.

**Report the count in each category.** That census is a deliverable in itself — it tells the planner
where the remaining risk is.

**A2.2 Never log secrets or content.** No clipboard text, no notification bodies, no message bodies, no
file contents, no TLS key material. Serials, addresses, states, error types and counts are fine. **This
is a hard rule and a harness check must enforce it** (see A3.3).

**A2.3 The sticky-error surface must be honest.** `ConnectionSupervisor` already carries a sticky error
concept — **verify how it actually behaves** (my hypothesis, unverified: it holds the last error and
clears on a successful connect). Requirements: an error that has been resolved must **not** keep
showing; an error that persists must **not** be replaced by a vaguer one; and "Searching" must never be
displayed while a known, unresolved error exists — that is the state that makes a user think the app is
working when it is not.

**A2.4 Every user-facing string in this path is plain language.** No adb output, no exception type
names, no error codes. D-009's shell box is the only place raw text is allowed. **If you find raw text
reaching the UI, that is a defect — fix it and name it in the report.**

**A2.5 Do not restructure the state machine.** No new states, no changed transitions, no reordering of
transport ranking (USB > wireless ADB > Direct TLS). **This part adds visibility, not behaviour.** If
you believe a transition is genuinely wrong, **report it — do not change it.**

## A3. The work

1. **The catch-block audit and the logging it produces** (A2.1), across the six named files.
2. **Plain-language pass** on user-facing strings in that path (A2.4).
3. **`tools/presencesim`** — new harness, following the conventions of `storesim`/`outboxsim`/
   `homecachesim`/`applaunchsim` exactly (numbered sections, `Check`/`CheckSub`, temp roots, exit 0/1,
   `FindRepoRoot` handling both CWDs). It must include:
   - **A crude source-text check over all six files that fails on any `catch` block with neither a log
     call nor an explanatory comment.** This is the anti-silence guard and it is the most valuable thing
     in this session. Comment it as crude and state exactly what it protects.
   - **A crude check that no `Log(` call in those files mentions a body/clipboard/content-shaped
     identifier** (A2.2), in the style `storesim` §11 already uses.
   - Any pure state/string logic you can call directly rather than model.

## A4. Part A acceptance

2. `tools/presencesim` green, exit 0. **Paste the catch-block census.**

# PART B — package it so someone other than the owner can install it

## B1. Why

Linc has never been installed by anyone but its author, from anywhere but a build output directory. M12
is the last milestone before the feature backlog (M4, M13), and **"it builds on my machine" is not a
beta.**

## B2. Decided design

**B2.1 Establish the truth first, and report it before changing anything.** What does a Release build
actually produce today? Does `-p:Configuration=Release` even succeed — **the entire project has only
ever been built Debug**, so treat a Release failure as expected news, not a disaster. Does the output
run from a copied folder on a machine without the SDK? **Report what you find before you fix it.**

**B2.2 Produce a self-contained folder that runs from a copy.** Whatever the packaging mechanism (a
publish profile, an MSBuild target, a script under `tools/`), the deliverable is: **a directory that can
be zipped, moved, and launched** — carrying the bundled scrcpy (`SCRCPY/Custom/bin/`, ~98 mingw64 DLLs),
`adb`, the companion APK that M2b injects, and the app's own assets. **Verify each of those four is
present in the output by listing them**; a missing scrcpy DLL or a missing APK turns into a runtime
failure on someone else's machine, which is exactly what this part exists to prevent.

**B2.3 Version it.** A single version number, set in one place, surfaced in Settings so a beta tester can
report "I'm on 0.9.1". Follow whatever versioning the csproj already has if any.

**B2.4 First-run on a clean machine must not assume the author's environment.** Hardcoded paths to
`C:\Users\<you>\…`, `<repo-root>/…`, the MSYS2 prefix, or the SDK are **bugs**. **Grep the
desktop source for absolute paths and report every one you find**, fixed or not. (D-050 is precedent:
scrcpy baked in the MSYS2 prefix and failed on a clean run — the same class of bug, already paid for
once in this project.)

**B2.5 Do not build an installer, an updater, or a signing pipeline.** A zippable folder is the goal.
Installers are their own milestone.

**B2.6 Do not commit anything, and do not add build output to the repo.** If packaging produces
artefacts, they go somewhere ignored. **Check `.gitignore` covers whatever you produce** and say so.

## B3. The work

1. Whatever `DESKTOP/Linc.Desktop/Linc.Desktop.csproj` / a publish profile / a `tools/` script needs to
   produce B2.2's folder.
2. **`Views/SettingsPage.xaml`** — the version string (B2.3), following the existing card conventions.
   **Do not restyle the page.**
3. **`tools/packagesim`** — new harness that verifies the **packaging inputs** without needing a full
   publish: that the four payload sets exist at their expected source paths, that the csproj still
   copies `SCRCPY/Custom/bin/**/*`, and **a crude source-text check that no `.cs` file in
   `DESKTOP/Linc.Desktop/` contains an absolute `C:\Users\` or `D:\delowe` path** (B2.4). Conventions as
   above.

## B4. Part B acceptance

1. MSBuild x64 Debug → 0 errors (unchanged). **Release attempted, and its result reported honestly** —
   success or failure, with the errors quoted if it fails. **A failed Release build is an acceptable
   outcome for this session** provided it is diagnosed and reported; do not hack around it.
2. `tools/packagesim` green, exit 0.
3. **One negative proof against a PRODUCTION file:** introduce an absolute `C:\Users\` path into a
   desktop `.cs` file → the check fails → restore → green.
4. Full regression: `presencesim`, `mirrorsettingssim`, `applaunchsim`, `appssim`, `homelayoutsim`,
   `displaysim`, `homecachesim`, `storesim`, `synccachesim`, `outboxsim`, `apkinstallsim`, `desktopsim`
   (ADB section honest either way) all green.
