## 1. 🔴 PART A — a second phone cannot be added, and I believe I know why

**Owner's report:** connecting a **new** phone over USB and enabling USB debugging, the *"Allow USB
debugging / Trust this computer"* prompt **never appears**, so the device can never be added.

**PLANNER'S HYPOTHESIS — STRONG, EVIDENCE-BACKED, BUT VERIFY BEFORE IMPLEMENTING.** Three facts line up:

1. **`BRAIN.md` / M2b already record this as a known limitation (D-037):** *"adding a 2nd phone while
   the first is connected won't complete — single active link."* The owner is doing exactly that.
2. **In the owner's own terminal this week,** `adb tcpip 5555` failed with
   **`error: more than one device/emulator`** while two devices were attached.
3. **That error is what every un-targeted adb command returns with two devices present.**

**So the likely cause is that the pairing / onboarding path issues adb commands WITHOUT `-s <serial>`,
and with a phone already attached every one of them errors out before it ever reaches the new device.**
The prompt never appears because nothing is talking to the new phone at all.

**A1. Verify first.** Grep every adb invocation reachable from onboarding, pairing and device-add
(`ConnectionManager`, `AdbServerHost`, the M2b onboarding path, `ToolLocator` consumers). **Report which
ones carry a device selector and which do not.** That list is the deliverable even if the fix is small.

**A2. Target every one of them.** Every adb command in a device-scoped path must name its device —
`-s <serial>` or the live transport id. **Note from BRAIN:** the bare serial `<your-device-serial>` is *not*
directly addressable over wireless; `-s` must use the live transport where that applies. **Untargeted
commands are only acceptable for genuinely global operations (`devices`, `start-server`), and those must
be commented as such.**

**A3. Detect and explain `unauthorized`.** `adb devices` reports a device as `unauthorized` when the
trust prompt is pending or was dismissed. **Today that state is invisible to the user.** Surface it in
plain language — *"Your phone is asking whether to trust this PC. Unlock it and tap Allow."* — and
**recover automatically** once it flips to `device`, with no restart and no re-run of the wizard.
**Poll, do not sleep a fixed interval.**

**A4. The private adb server port.** The owner's own M13 spec said: *"run on a private server port so an
unrelated tool calling `adb kill-server` cannot break you mid-session."* It was never implemented. This
machine has Android Studio's SDK adb installed as well as Linc's bundled copy, and **two adb servers of
different versions fighting over port 5037 will kill each other's server repeatedly** — which also
prevents an auth handshake from completing.

**Verify before implementing:** run `Get-Process adb | Select Id, Path` and report what is actually
running. **If more than one adb, or one outside Linc's bundle, set `ANDROID_ADB_SERVER_PORT` (5038) for
every adb invocation Linc makes** and say so. **If only Linc's adb is running, do NOT make this change**
— report that the hypothesis failed.

**A5. Two phones at once — the honest answer.** **D-037 stands: Linc supports ONE active link.** Do not
attempt concurrent live links; that is an architectural change and is **out of scope**.

What must change is that the limit becomes **visible and graceful** instead of a silent hang:
- Adding/pairing a new device **must work while another is connected** (that is A2 — targeting).
- When a second device is *ready* and the user activates it, **switch cleanly**: tear the first link
  down, say so in plain language, bring the second up.
- If a switch cannot proceed, **say why and what to do** — *"Linc talks to one phone at a time.
  Disconnect <name> to use <new name>."* Never a spinner that never resolves.
- **Put the decision in a pure static** — `DecideDeviceSwitch(current, requested, currentState)` — so
  the harness proves it without hardware.
