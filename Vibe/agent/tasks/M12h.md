## 1. The symptom, and what is already ruled out

**The owner reports: the tray icon is now good (M12e Part A is confirmed working), but after using the
"Start Linc when I sign in" toggle, Linc does not appear in Windows Settings → Startup apps.**

**Ruled out already — do not re-investigate these.** The planner read the code:

- DI registration exists: `App.xaml.cs:74` → `new StartupRegistration(log: …)`, so `subKeyPath` takes its
  default (`Software/Microsoft/Windows/CurrentVersion/Run`) — it is pointed at the **real** key, not a
  test key.
- The setter is wired: `SettingsViewModel.cs:189-205` calls `SaveStartWithWindows(value)` and then
  `_startup.Enable(Environment.ProcessPath ?? …)` / `Disable()`.
- The XAML toggle is `IsOn="{x:Bind ViewModel.StartWithWindows, Mode=TwoWay}"` (`SettingsPage.xaml:144`).
- M12g checked the registry and found **no `Linc` value** under the Run key.

**So the shape of the code is right and the key is not being written. The question is why.**

## 2. Diagnose — establish which branch, then stop and fix only that

**Add a temporary diagnostic if you need one, but remove it before you finish.** Determine which of these
is true and **say so explicitly in the report:**

**Branch A — the setter never runs.** The binding does not deliver the flip. Check by logging at the top
of the setter and toggling. If the setter is not reached, the fault is in the view layer — and note that
`StartWithWindows` has **no backing field and no `[ObservableProperty]`**; its getter reads straight
through to `_registry`. **If `SaveStartWithWindows` does not actually persist, the getter returns the old
value, and a `TwoWay` `x:Bind` can revert the toggle and make it look like nothing happened.**

**Branch B — the setter runs and `Enable()` throws.** `Enable` catches everything and logs at `Error`,
so a failure is **completely invisible in the UI**. Read `%LOCALAPPDATA%\Linc/logs/*.ndjson` for a
`StartupRegistration: Enable failed` line and paste it.

**Branch C — the key IS written and Windows is not showing it.** Read the value back with
`Get-ItemProperty` immediately after toggling. If it is present, the bug is not ours — but **check what
path it holds**: a Debug-build path under `bin\x64\Debug\…` is a real problem worth reporting even though
it is not this bug.

**Suspect Branch A first.** `SaveStartWithWindows` was added to `DeviceRegistry` by M12e, and M12e's
report was never reviewed. **Verify that the new field is actually written by `Persist()` and read back
by the load path** — the settings record is positional, and M12e was told to append the field to the end.
**If it was appended to the record but omitted from the `Persist()` construction, the preference never
survives and the getter always returns `false`.** That single defect would produce exactly this symptom.
*Planner's hypothesis — verify before implementing.*

## 3. The fix

Fix **only** the branch you proved. Then, regardless of branch, close the observability gap that made
this hard to see:

- **`Enable()` and `Disable()` must log on SUCCESS, not only on failure** — at `Info`, naming the value
  written and the path. A silent success is indistinguishable from a silent failure, which is why this
  cost a round trip. This is the standing "a silent catch is a bug factory" rule.
- **If Branch A is the cause, add a round-trip check to `autostartsim`**: save the preference, reload the
  registry from disk, assert it reads back `true`. M9b's `storesim` does this for
  `NotificationHistoryEnabled` — copy that shape.
