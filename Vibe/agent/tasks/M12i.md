# PART B — `canSleep` is wrong on this machine, and probably on most modern ones

M4b implemented `canSleep` with `IsPwrSuspendAllowed()` and **runtime-verified it returns `false` on the
owner's machine — while Sleep works perfectly from that machine's own Start menu.**

The agent's diagnosis, which I find convincing but have **not** verified myself — *treat it as a
hypothesis and confirm it before implementing*: `IsPwrSuspendAllowed()` reports on **legacy ACPI S3**
only, and modern machines use **Modern Standby (S0 low-power idle)** instead. It correctly judged the
fuller fix out of M4b's scope and flagged it rather than shipping a wrong assumption silently — the
right call, and the reason this task exists.

**The user-visible effect: the owner's Sleep button is disabled for no good reason.**

**B1.** Use `GetPwrCapabilities` (`SYSTEM_POWER_CAPABILITIES`) and report `canSleep: true` when **either**
legacy sleep **or** `SystemS0LowPower` is available. The struct is large; you only need those fields —
declare it accurately, but do not gold-plate the rest.

**B2.** Keep it a **read-only capability query.** Do not add a code path that can suspend the machine.

**B3.** Extend `pccontrolsim` so the capability logic is exercised as a **pure function** over the
struct's flags — `(s3Allowed, s0LowPower) → canSleep` — so it is testable without a machine that has
either. **Do not make the harness call the real Win32 API**; that is what made this untestable the
first time.

**B4.** Report what `canSleep` evaluates to on this machine after the change, and how you obtained that
without executing anything. **M4b's throwaway-console-outside-the-repo + reflection approach is the
established pattern here — reuse it, and delete it again.**
