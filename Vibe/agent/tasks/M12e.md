# PART A — the tray icon

## A1. What is known, and what is only suspected

**Known:** M12b's startup crash logging exposed an exception mentioning **`ToSmallIcon`**. It has been
described as non-fatal and it was invisible for the entire life of the project before M12b. Nobody has
read the stack trace since.

**Also known, from the source:**
- `MainWindow.xaml:156-169` declares the `<tb:TaskbarIcon x:Name="TrayIcon">` with
  **`IconSource="ms-appx:///Assets/linc.png"`** (line 158).
- `MainWindow.xaml.cs:45` calls `TrayIcon.ForceCreate()` from the constructor, immediately after
  `InitializeComponent()`.
- `MainWindow.xaml.cs:47` sets the **window** icon with
  `AppWindow.SetIcon(Path.Combine(AppContext.BaseDirectory, "Assets", "AppIcon.ico"))` — a filesystem
  path, and this one has always worked.
- `Assets/` contains exactly two files: `AppIcon.ico` (8,115 bytes) and `linc.png` (911 bytes). Both
  reach the output via the `<Content Include="Assets/**/*">` glob at `Linc.Desktop.csproj:25`.
- The app is **`<WindowsPackageType>None</WindowsPackageType>`** (`Linc.Desktop.csproj:18`) — unpackaged.
- `H.NotifyIcon.WinUI` is pinned to **2.2.0** (`Linc.Desktop.csproj:58`). Do not upgrade it.

**PLANNER'S HYPOTHESIS — VERIFY BEFORE IMPLEMENTING.** I suspect the `ms-appx:///` icon source is the
cause: H.NotifyIcon has to convert that `IconSource` into a Win32 `HICON` (the `ToSmallIcon` path), and
this app has no package identity. **I have not read the stack trace and I am not asserting this.** The
proven-working pattern for an icon in this very file is the filesystem path on line 47.

# PART B — start Linc when I sign in

Re-read this file from the top, then continue without pausing.

## B1. The shape

Opt-in, **default OFF**, per-user, no admin. The mechanism is the **HKCU Run key** — it works for an
unpackaged app, needs no elevation, and Windows Settings → Startup apps and Task Manager both surface it,
so the user can always turn it off outside our UI. **No Task Scheduler. No HKLM. No elevation prompt.**

## B2. New file: `DESKTOP/Linc.Desktop/Services/StartupRegistration.cs`

Dependency-free so a harness can compile it alone. Do **not** reference it from `DeviceRegistry.cs`
(see B3 for why).

Pure statics, all four independently testable:

- `const string RunKeySubPath = @"Software\Microsoft\Windows\CurrentVersion\Run"`
- `const string RunValueName = "Linc"`
- `static string BuildRunCommand(string exePath)` → the exe path **wrapped in double quotes**, followed
  by a space and `--startup`. The quotes are load-bearing: this app is developed under
  `<repo-root>/...` and ships as a copied folder that may land anywhere, including a path
  with spaces. An unquoted path with a space is silently ignored by Windows at sign-in.
- `static bool NeedsRewrite(string? existing, string desired)` → ordinal-**ignore-case** comparison,
  `true` when they differ or `existing` is null/empty.
- `static bool IsStartupLaunch(IEnumerable<string> args)` → true when any arg equals `--startup`,
  case-insensitively.

Instance members, with the subkey path **injectable**:

- `StartupRegistration(string subKeyPath = RunKeySubPath)` — the D-057 pattern, exactly as
  `DeviceRegistry(string? rootPath = null)` does it. Production DI resolves the default; **the harness
  passes a throwaway key and can therefore never touch the real Run key.**
- `bool IsEnabled()`, `void Enable(string exePath)`, `void Disable()` — all under `HKEY_CURRENT_USER`,
  all catching and logging rather than throwing into a caller.

## B3. `DeviceRegistry` gains the preference — and only the preference

- `bool StartWithWindows { get; }` on `IDeviceRegistry`, **default `false`**, plus
  `void SaveStartWithWindows(bool enabled)`. Follow M9b's `NotificationHistoryEnabled` shape exactly:
  in-code default `false`, **and** `?? false` in the load path, so an upgraded install with no stored
  key is as quiet as a fresh one.
- **Append the new field to the END of the settings record positional parameter list**, as M9b's two
  fields were. Appending keeps an older `settings.json` deserializable; inserting anywhere else silently
  reassigns every field after it. Update the `Persist()` construction to match.
- **THE RECURRING CSPROJ GOTCHA — CHECK IT, DO NOT ASSUME.** `tools/devicesim` and `tools/blescan`
  `<Compile Include>` the real `DeviceRegistry.cs` with no `ProjectReference` (D-036). Adding a plain
  `bool` should need no csproj change; **adding a reference from `DeviceRegistry.cs` to
  `StartupRegistration.cs` would break both harnesses.** This has bitten three times (M8a, M5b, M11).
  **Keep them decoupled:** `DeviceRegistry` stores the preference, `StartupRegistration` writes the
  registry, and the Settings view model is the only thing that calls both. **Build both harnesses and
  paste the result.**

## B4. The Settings toggle

Add a toggle to `Views/SettingsPage.xaml` + `ViewModels/SettingsViewModel.cs`, modelled on the
**notification-history card**, which is the good example in this codebase: `TwoWay` to a property whose
setter calls a real `Save…` method.

**This is where M5c-2 shipped dead UI behind a green build** — a `OneWay` binding to a read-only property
is legal XAML and compiles clean. The setter must call **both** `SaveStartWithWindows(...)` **and**
`StartupRegistration.Enable(...)` / `.Disable()`. Setting the preference without writing the key, or
writing the key without persisting the preference, are both defects.

Caption, plain language (CONTRIBUTING.md — no jargon reaches the UI):
**"Start Linc when I sign in"** with a sub-line **"Linc opens quietly in the notification area."**

## B5. Reconcile on every launch

The app ships as a **copied `publish/` folder**, so its exe path changes whenever the owner moves or
re-copies it, leaving a stale Run entry pointing at nothing.

In `App.OnLaunched`, **inside the existing fire-and-forget `Task.Run` block** (lines ~144-159) — do not
add a second one and do not block launch: if `registry.StartWithWindows` is true and
`NeedsRewrite(currentValue, desired)`, rewrite the value. Log at `Info` when it rewrites.

## B6. Silent start

- `OnLaunched`'s `LaunchActivatedEventArgs` does **not** carry the command line for an unpackaged app —
  read it from `Environment.GetCommandLineArgs()`.
- **STILL CALL `_window.Activate()` EVEN ON A STARTUP LAUNCH.** M9e measured that the view models are
  constructed **synchronously as part of `Activate()`**; skipping it would leave everything in
  `AppShellViewModel` unstarted and the app would sit in the tray connected to nothing. Activate, **then
  immediately hide the window to the tray.**
- **Reuse the existing close-to-tray mechanism** — the app already hides rather than exits on
  `CloseMainWindow`. Find how it does that and call the same thing. **Do not invent a second hiding
  path.** Report which mechanism you found and reused.

## B7. New harness: `tools/autostartsim`

A plain `net8.0` console, following the existing harnesses' shape.

- The four pure statics, including: `BuildRunCommand` on a path **containing a space** round-trips with
  quotes intact; `NeedsRewrite` is case-insensitive; `IsStartupLaunch` matches `--startup` and rejects a
  bare `startup`.
- `Enable` / `IsEnabled` / `Disable` round-trip **against a throwaway subkey**
  (`Software/Linc/AutostartTest`), deleted in a `finally`.
- **A crude source-text check** that reads `Views/SettingsPage.xaml` and `ViewModels/SettingsViewModel.cs`
  and fails if the toggle is not `TwoWay`, or if `SaveStartWithWindows` is absent from the setter path.
  The behaviour lives in a view the harness cannot call into, so text is the only lever — this is the
  M5c-3 pattern and it is why M9b's proof was hollow.
