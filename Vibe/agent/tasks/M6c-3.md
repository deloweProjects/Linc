## 1. What the owner asked for, and what it replaces

M6c-2 put Apps in the right column **below** the tabs panel, with the whole column scrolling to reach
it. The owner has used it and rejected that: **Apps must be visible without scrolling the column.**

The new arrangement, in the owner's words: Apps is **visible**, you **scroll within it**, and there is
a **size adjuster between it and the tabs above**.

So the right column becomes: **tabs panel on top → a draggable horizontal splitter → Apps below**, both
always on screen, each scrolling internally. Dragging the splitter trades height between them.

---

## 2. Decided design

**2.1 Replace the outer `ScrollViewer` with a three-row `Grid`.** The right column container becomes
a `Grid` with rows: `[TabsPane (star or pixel height)] [splitter (Auto)] [Apps (star or pixel)]`.
There is **no column-level scrolling any more** — remove `RightPane`'s `ScrollViewer` entirely.

**2.2 DELETE the `TabsPane` height-sync.** `OnRightPaneSizeChanged` and the `TabsPane.Height`
assignment exist **only** because a `ScrollViewer` measures its content with infinite height. A `Grid`
row gives `TabsPane` a bounded height for free, which is the proper fix. **Remove the handler, the
`SizeChanged` hook and the load-bearing XAML comment about it** — and make sure `TabsPane` no longer
carries an explicit `Height`, or the splitter will fight it.
*(The invariant that mattered still holds and still matters: `TabsPane` must never be measured with
unbounded height, or the notification/messages/calls `ListView`s lose their internal scrolling. A
bounded grid row satisfies it structurally.)*

**2.3 Apps scrolls internally.** A `ScrollViewer` **inside** the Apps card, wrapping the
`ItemsRepeater`, vertical Auto, horizontal Disabled. Keep the icon+name `UniformGridLayout` tiles from
M6c-2 exactly as they are.

**2.4 The splitter matches the existing vertical one.** There is already a working horizontal-drag
splitter between the two panes (`Splitter`, `OnSplitterDrag` in `HomePage.xaml.cs`, with the M6b
pane-order awareness). **Mirror its approach for the vertical direction** — same visual weight, same
resize cursor treatment (`InputSystemCursorShape.SizeNorthSouth` here), same clamping style. *Your
judgement* on whether to share code with the existing handler or write a sibling; say which and why.

**2.5 Clamp both ways.** Neither pane may be dragged out of existence. Give the tabs panel a sensible
minimum (it holds list content — a few hundred px) and Apps a minimum of roughly **two tile rows**, so
the section always shows it is a grid. Derive the Apps minimum from the tile height rather than
hardcoding a magic number where you reasonably can.

**2.6 Persist the split, per device.** Add a nullable height (e.g. `AppsPaneHeight`) to
**`HomeLayout`** and save it when the drag ends. **This is cheap and safe: `HomeLayout` already sits
in every consuming `tools/*.csproj`, so adding a field to it does NOT change `KnownDevice`'s parameter
list and does NOT require any csproj change.** Do not touch `KnownDevice`.
- Null means "use the default split" — pick a sensible default (roughly 65/35 in the tabs panel's
  favour) and state what you chose.
- **Guard the echo.** Saving raises `HomeChanged` → `RefreshSections`; that must not feed back into a
  resize or a second save. This project has hit the echo bug three times; use the established
  "differs from the known value" guard.

**2.7 Swap sides keeps working.** `ApplyPaneOrder` currently moves `RightPane`. It must now move the
new `Grid` container — tabs, splitter and Apps travel together. The M6b vertical splitter must still
resize the **widgets** pane, in the intuitive direction, in both orientations.

**2.8 Apps stays non-interactive this session.** Clicking a tile does nothing; **M7a** makes tiles
launch apps. Do not add click handling here.
