## 1. 🔴 PART A — a second phone cannot be added

**Owner's report:** with one phone already connected, plugging in a **new** phone over USB and enabling
USB debugging never produces the *"Allow USB debugging / Trust this computer"* prompt, so the device can
never be added.

### PLANNER'S HYPOTHESIS — evidence-backed, but VERIFY BEFORE IMPLEMENTING
Three facts line up:
1. **BRAIN/M2b already record this as D-037:** *"adding a 2nd phone while the first is connected won't
   complete — single active link."* The owner is doing exactly that.
2. **In the owner's own terminal**, `adb tcpip 5555` returned **`error: more than one device/emulator`**
   with two devices attached.
3. That error is what **every un-targeted adb command** returns when two devices are present.

**So the likely cause is that the pairing / onboarding / device-add path issues adb commands without
`-s <serial>`, and with a phone already attached every one of them errors out before it ever reaches the
new device.** The prompt never appears because nothing is talking to the new phone at all.

**This is a hypothesis. `grep` locates; it never concludes.** Read the enclosing block of every hit
before you describe its behaviour.

### A1 — Verify first, and produce the list
Grep every adb invocation reachable from onboarding, pairing and device-add — start at
`Services/ConnectionManager.cs`, `Services/AdbServerHost.cs`, `Services/PhoneSetupCommands.cs`,
`Services/PhoneSetupService.cs`, `Services/ConnectionSupervisor.cs`, `Services/ToolLocator.cs` consumers,
and the M2b onboarding path (`Services/OnboardingFlow.cs`, `ViewModels/OnboardingViewModel.cs`).

**Report the full list: every adb call site, and whether it carries a device selector.** That list is a
deliverable in its own right even if the fix turns out to be small.

### A2 — Target every device-scoped call
Every adb command in a device-scoped path must name its device — `-s <serial>` or the live transport id.
**Note from BRAIN:** the bare serial `<your-device-serial>` is **not** directly addressable over wireless; `-s`
must use the live transport where that applies. Untargeted calls are acceptable **only** for genuinely
global operations (`devices`, `start-server`, `version`), and each one must carry a comment saying so.

### A3 — Detect and explain `unauthorized`
`adb devices` reports a device as `unauthorized` while the trust prompt is pending or was dismissed.
**Today that state is invisible to the user.** Surface it in plain language — *"Your phone is asking
whether to trust this PC. Unlock it and tap Allow."* — and **recover automatically** when it flips to
`device`: no app restart, no re-run of the wizard. **Poll for the transition; do not sleep a fixed
interval.** (Fixed sleeps are why `cleanroomsim` failed deterministically in M4a — see BRAIN.)
Raw adb text never reaches the UI (GUARDRAILS).

### A4 — The private adb server port
The M13 spec said: *"run on a private server port so an unrelated tool calling `adb kill-server` cannot
break you mid-session."* It was never implemented. This machine also has Android Studio's SDK adb, and
**two adb servers of different versions fighting over port 5037 kill each other's server repeatedly** —
which can also stop an auth handshake completing.

**Verify before implementing:** run `Get-Process adb | Select-Object Id, Path` and report what is
actually running.
- **If more than one adb, or one outside Linc's bundle:** set `ANDROID_ADB_SERVER_PORT` (**5038**) for
  every adb invocation Linc makes, in one place, and say so.
- **If only Linc's bundled adb is running:** **do not make this change** — report that the hypothesis
  failed. A wrong "fix" here costs the next session.

### A5 — Two phones at once: the honest answer
**D-037 stands: Linc supports ONE active link.** Concurrent live links are an architectural change and
are **out of scope.** What must change is that the limit becomes **visible and graceful** instead of a
silent hang:
- Adding/pairing a new device **must work while another is connected** (that is A2).
- When a second device is ready and the user activates it, **switch cleanly**: tear the first link down,
  say so in plain language, bring the second up.
- If a switch cannot proceed, **say why and what to do** — *"Linc talks to one phone at a time.
  Disconnect &lt;name&gt; to use &lt;new name&gt;."* Never a spinner that never resolves.
- **Put the decision in a pure static** — `DecideDeviceSwitch(current, requested, currentState)` — so the
  harness proves it with no hardware attached.
