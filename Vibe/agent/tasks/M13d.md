## 1. Context — you raised five items, here are the rulings

The M13 chain is **accepted**. These are the follow-ups. **Three are code changes, two are
confirmations with no work attached.**

### 1.1 ✅ RULING: the `gen` filter is `>=`. **Change your implementation.**

You implemented strictly-greater; `PROTOCOL.md` said "lower than". **`PROTOCOL.md` was right and has
been clarified — the task file's "reject equal-or-stale" was my error.**

`gen` marks the **link epoch**, not the message, and several messages legitimately share one epoch.
**The case that proves it: `adb tcpip 5555` rebinds `adbd` with no link event**, so the phone
re-announces the new port under the *same* `gen`. Strictly-greater discards it and the whole promotion
optimisation silently never fires — which would present as "promotion doesn't work" and cost a session
to find. Same shape for a `tls → tcpip` mode change or a re-announce after a failed `adb.ack`.

**Change `ShouldAccept` to accept equal, reject strictly lower.** Within an epoch, **last-write-wins**;
the control socket is a single ordered stream so ordering is already guaranteed. **Update the harness
checks that currently assert equal is rejected — they are asserting my mistake.** Add one that proves
the re-announce-at-same-gen case is accepted.

### 1.2 ✅ RULING: your `serial` decision was correct. Keep it.

You are right that an unprivileged app cannot read its own ADB serial (`Build.getSerial()` has needed
`READ_PRIVILEGED_PHONE_STATE` since Android 10), so requiring it would reject every real announcement.
Verifying `get-serialno` against `DeviceRegistry.PairedSerial` and treating the announced value as a
cross-check is **stronger** than trusting the phone's claim. `PROTOCOL.md` now marks `serial` optional
and says so. **No code change — confirm the implementation matches and move on.**

### 1.3 ✅ RULING: not stopping at the gate was the right call.

**My gate and my §2 contradicted each other** — §1 said "stop if the peer address is not exposed", §2
said "describe the smallest change that would expose it, do not restructure the transport stack." You
took §2's path and flagged it. That was correct judgement.

The gate existed to stop three milestones being built on a **false premise**. The premise was not false:
the address existed and was knowable, it was merely not plumbed. **Master-verified: `PeerAddress` /
`ControlArrived` total 12 references across 4 files — one signature widened and consumed, not a
restructure.** Keep it. **No change.**

### 1.4 🔧 FIX: give `StartSpeculative()` its trigger.

The race is built and proven and nothing calls it, which makes it dead code. **The hook is the thing
M13a just plumbed:** subscribe in `HotspotLinkService` to the control-connection-established event that
now carries `IPEndPoint?`, and when that endpoint is present **and** `SelectEndpoint` judges it
hotspot-shaped (same-subnet with one of our own interfaces), fire `StartSpeculative()`.

**This needs no transport-path change** — that is why §6 forbade touching it and why you were right to
stop rather than guess. The subscription lives entirely in `HotspotLinkService`.

**Guard it:** fire at most once per `gen`, and never when a verified ADB connection for that endpoint
already exists. Prove both in `hotspotsim`.

### 1.5 ✅ RULING: the deferred sweep stays deferred. Document the gap where a user will hit it.

Your measurement (~44–175 s on-device) is exactly why the task file bounded it. **Do not build it.**

The residual gap is narrow — a phone where **both** the system properties are unset **and** NsdManager
fails, on a **first** connection, before any promotion. **The escape hatch already exists in the
protocol: `adb.arm` with `prefer: "tcpip"`** asks the phone to arm legacy tcpip on a *known* port, which
sidesteps random-port discovery entirely.

**Do:** make the desktop send `adb.arm { prefer: "tcpip" }` when it has received no usable announcement
within a short window (pick a value, state it), and log one plain-language line naming the situation.
**Do not** add a UI for it in this task.
