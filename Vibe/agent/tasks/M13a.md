## 3. The work

### 3.1 The role rule — `Services/HotspotRole.cs`, pure and testable

Both sides run identical logic; whoever hosts ends up listening, whoever joined ends up dialling:

```
gw = default_gateway_for(iface)
if gw is null or gw == my_address_on(iface):  role = AP      → LISTEN
else:                                          role = CLIENT  → DIAL gw:PORT
```

**Put the decision in a pure static** — `DecideRole(string? gateway, string myAddress) → Role` — so a
harness tests it with no network. The Win32 lookup (`GetBestRoute2`, or `Get-NetRoute
-DestinationPrefix 0.0.0.0/0`) lives in a thin wrapper around it, not inside it.

**Belt and braces, per the spec:** both sides should run the listener unconditionally and only the
client dials. A duplicate connection is deduped later by `gen` (M13b); a missing one is not recoverable.

### 3.2 Address resolution — `Services/HotspotAddress.cs`, pure

Resolution order, and **the filter is the load-bearing part:**

1. the control socket's peer address, **only if it is inside one of my own interfaces' subnets**;
2. an announced address from `addrs` (M13b — leave the hook, do not implement the message here);
3. the default gateway of the hotspot interface (covers the phone-is-AP role).

**Pure static: `SelectEndpoint(peer, announced[], myInterfaces[]) → chosen`,** rejecting anything not
same-subnet. **Android advertises mobile-data and secondary-interface addresses that are unreachable
from the hotspot segment; each unfiltered one costs a full connect timeout.**

**Also handle IPv6 explicitly:** if the peer address is a **link-local IPv6** address, prefer an IPv4
candidate — `adb connect [fe80::x%iface]:port` is unreliable on Windows. Return the IPv4 entry when both
exist. Cover this in the harness.

### 3.3 The connect path — hardcoded port 5555, manually armed

**No port discovery and no announce message in this task** (both are M13b). Assume `adb tcpip 5555` was
run once by hand. The desktop:

- `adb disconnect <endpoint>` **before** every connect attempt — the adb server caches stale endpoints
  and silently refuses the replacement. **Non-negotiable; this is the most common "it worked yesterday"
  bug.**
- `adb connect <ip>:5555`, then **verify all three**: output contains "connected to", `get-state` is
  exactly `device`, `get-serialno` matches the expected serial. **Reachability is not identity.**
- Pre-warm: `adb start-server` at app launch, so the 200–500 ms cold start is not on the hot path.
  **Check whether `AdbServerHost.cs` already does this** — if so, say so and change nothing.

**Bind the source address to the hotspot interface** where the API allows. With a VPN or Ethernet also
up, connects can leave via the wrong NIC.

### 3.4 `tools/hotspotprobe` — the owner's one-command diagnostic

**This is the most valuable deliverable in this task**, because it is what turns the owner's hand-test
into data. A console the owner runs **while a hotspot link is up**, printing a labelled report:

- every interface: name, IPv4, prefix, default gateway, and the role `DecideRole` picks for it;
- `adb devices` output verbatim;
- whether TCP 5555 on the resolved peer/gateway address accepts a connection, with elapsed ms;
- if it connects: `get-state` and `get-serialno`;
- whether the Windows firewall profile for that interface is **Public** — *"Windows classifies fresh
  hotspot links as Public and drops inbound traffic on the app's listen port. This presents as 'the
  phone just isn't there', which sends you debugging the wrong layer."* **Report it loudly.**

**It must be read-only: no `adb tcpip`, no firewall changes, no interface changes.** It measures and
prints. **It must run and print something useful on a normal LAN too**, so you can exercise it now.

### 3.5 `tools/hotspotsim` — the pure-logic harness

`DecideRole` (AP / client / no-gateway), `SelectEndpoint` (same-subnet accept, foreign-subnet reject,
link-local-IPv6 → IPv4 preference), and the disconnect-before-connect ordering asserted as a
source-text check if it cannot be called directly.
