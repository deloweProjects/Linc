## PART E — wallpaper: unblur it

> *Result line, written on finishing Part E:* premise confirmed and sharpened — no blur filter
> exists; 48 px → 1600 px longest edge, PNG → JPEG; measured; scrim dial added, default 0.

### E1 — what the code actually does

**The task's inference is correct — it is a two-sided change — and the reality is sharper than
stated: there is no blur to remove.**

`ANDROID/app/src/main/java/app/linc/android/service/WallpaperProvider.kt`, as it stood:

- `private const val THUMB_WIDTH_PX = 48` (line 21).
- `refreshLocked()` scaled the wallpaper to **48 px wide**, height proportional
  (`createScaledBitmap(bitmap, 48, height, true)`), then `compress(PNG, 100)`.
- **The blur IS the downsample.** The file's own doc comment said so in as many words: *"Only the
  ~48 px downsample ever leaves the phone — downsampling* is *the blur, and full-res stays local."*

So **the phone produces both the blur and the size**, and there is no `RenderScript`, no
`BlurMaskFilter`, no shader — nothing to delete. Making it sharp is arithmetic on one constant plus
a format choice.

**Dimensions that were being sent:** 48 px wide by whatever the aspect gives. For the Pixel 7's
1080×2400 wallpaper that is **48×106**.

**The desktop side** (`Services/ThemeSyncService.cs`) is **size- and format-agnostic and always was**:
`FetchWallpaperAsync` fetches bytes via `connection.FetchBulkAsync("wallpaper", id, …)`, hands them to
`BitmapImage.SetSourceAsync`, and computes a dominant colour via `BitmapDecoder.CreateAsync`. Both are
format-sniffing WIC-backed decoders. Nothing on the desktop assumed 48 px or PNG.

The doc comments on the desktop side did claim otherwise — `ThemeSyncService.cs`'s
`Wallpaper` property and `HomeViewModel`'s field both said *"pre-blurred"*. Those comments now
describe what the code does.

### E2 — sent sharp, and the numbers

**Chosen bound: `MAX_DIMENSION_PX = 1600`, on the LONGEST edge, JPEG at quality 85.**

Three decisions, each with a reason:

1. **1600 on the longest edge, not a width.** A phone wallpaper is portrait, so bounding the width
   would leave the height unbounded on an unusual aspect. 1600 gives **720×1600** for a 1080×2400
   wallpaper — comfortably sharper than the widgets pane it sits behind (roughly 800×1300 physical px
   at 125% scaling), so `UniformToFill` downsamples rather than upscales.
2. **JPEG, not PNG.** This is the decision the measurement below actually forced.
3. **Never upscales.** A wallpaper already inside the bound is encoded at its own size.

**Measured**, running both pipelines over the same 1080×2400 source:

```
source                 1080x2400
BEFORE  48px  PNG q100 48x106            16,948 bytes
AFTER   1600  JPEG q85 720x1600          96,169 bytes   (5.7x)
(rejected) 1600  PNG    720x1600      2,054,364 bytes   (21.4x the JPEG)
pixel count                        226x more pixels
```

**5.7× the bytes for 226× the pixels.** The rejected row is the important one: keeping PNG at the new
size would have produced a **2 MB** payload — precisely the "several-megabyte payload is not
acceptable" the task rules out — so the format change is what makes the resolution change affordable.

**Honest limits on that measurement.** No phone is attached, so this is not the phone's own encoder
on the owner's own wallpaper. The source is **synthetic**, built with photographic statistics
(smooth multi-octave colour fields plus fine luminance grain, which is what actually drives
compressed size); I did not use the owner's real cached photos, which are theirs and not needed. A
real photograph has more high-frequency detail, so expect the real figure to land **higher than
96 KB — plausibly 150–400 KB**. The dimensions and the format are exact; the byte count is
representative. The PNG counterfactual is multi-megabyte on any realistic content.

### E3 — no protocol change, and mixed versions

**Both constants still 18** (pasted in §4 below). The bulk kind is still `wallpaper`, the message
shapes are untouched, and `DeviceStatusReporter`/`CompanionService` are unchanged — the phone still
advertises `wallpaperId` in status and still answers `"wallpaper" -> WallpaperProvider.thumbnail(id)`.
Only the **bytes behind an existing id** changed.

- **Old phone → this desktop:** sends the 48 px PNG exactly as before. The desktop decodes through
  format-sniffing decoders and renders it, unchanged. Nothing on the desktop reads or asserts a
  dimension or a format.
- **New phone → older desktop:** the older desktop uses the same two APIs
  (`BitmapImage.SetSourceAsync` and `BitmapDecoder.CreateAsync`), which decode JPEG and PNG alike, so
  it renders the sharp image. **Verified against the current source only** — I did not build or run
  an older desktop, and I am not claiming more than that.

The one desktop change Part E required is a **performance** guard, not a compatibility one:
`ComputeDominantAsync` walks every pixel, which was free at 48 px. It now asks the decoder for a
bounded `DominantScanEdge = 96` px version for that scan. The image the UI renders is still decoded at
full size.

### E4 — the scrim

**Constant name: `ScrimStrength`. File:
`DESKTOP/Linc.Desktop/Services/ThemeSyncService.cs`. Default: `0.0` — off, as asked.**

```csharp
public const double ScrimStrength = 0.0;
```

`ApplyWallpaperAccent()` still computes the same tinted fog colour, but its alpha is now the
full-strength value (`0xCC` dark / `0xDA` light) **scaled by `ScrimStrength`**. At `0.0` the brush is
fully transparent: the `Border` in `HomePage.xaml:62` still exists and still binds — it simply paints
nothing.

**For the owner: if text over the wallpaper becomes hard to read, change that one number.** 0.35 is a
light veil, 0.6 a strong one, 1.0 is exactly the pre-M15b appearance. The blur was doing double duty
as legibility protection and removing it removes that, which is why this is a named, documented dial
and not a silent zero.

I left the XAML default `<SolidColorBrush x:Key="WallpaperScrimBrush" Color="#CC101010" />` in
`Themes/MaterialExpressive.xaml` **unchanged**: `packagesim` asserts that exact neutral value as part
of M14's palette check, and it is only ever the pre-sync placeholder — `ApplyWallpaperAccent()` runs
inside `LoadWallpaperAsync` **before** `WallpaperChanged` fires, and the scrim Border is gated on
`HasWallpaper`, so the runtime value is always the one this dial produces.

## PART F — Apps off gives its space to Notifications

> *Result line, written on finishing Part F:* row **and** splitter row collapsed, restore path fixed,
> proven by breaking it.

The right column is the three-row grid M6c-3 describes: `TabsRow` (`65*`), the splitter row
(`Auto`), `AppsRow` (`35*`), with a persisted pixel split. Hiding the Apps `Border` alone left both
rows holding their share of the column — the gap the owner reported.

Changes:

- **`Views/HomePage.xaml`** — the splitter row is now named `AppsSplitterRow`, and `AppsSplitter`
  binds `Visibility` to `ViewModel.ShowApps`.
- **`Views/HomePage.xaml.cs`, `ApplyAppsHeight()`** — branches on `ShowApps` **first**, ahead of the
  echo filter, and zeroes `AppsRow` *and* `AppsSplitterRow` while giving `TabsRow` the whole column
  (`1*`). Checking first matters: a collapse must never be skipped as "a value we already applied".
- **The restore path**, which is the part that is easy to get wrong: collapsing sets
  `_appliedAppsHeight = null`, so switching Apps back on always re-applies the persisted split
  instead of being filtered out as an echo of a height the rows no longer have. `AppsSplitterRow`
  goes back to `Auto` on the way in.
- **`ShowApps` now re-runs the layout.** The `PropertyChanged` handler previously listened only for
  `AppsPaneHeight`, so toggling the section would not have re-laid-out until a device switch.
- **The `Loaded` re-clamp is guarded on `ShowApps`** — unguarded it would put a pixel height back on
  a row that Apps-off had just collapsed.

This is **removed**, not the *disabled* state: the Apps grid's `Opacity="{x:Bind ViewModel.AppsOpacity}"`
(the M6c "Border is not a Control" affordance for a pre-v16 phone) is untouched, and only one of the
two reclaims space.

## Things in `M15b.md` that were wrong or ambiguous

1. **Part E's premise is right, and understated.** §66's correction to `M15.md` is correct that this
   is two-sided — but there is **no blur filter anywhere**. "Remove the blur" (E2) has no referent:
   the blur is the 48 px downsample. Worth saying plainly, because a session that goes looking for a
   blur to delete will not find one and may conclude the file is wrong.
2. **`Views\HomePage.xaml:403` and `HomeViewModel.cs:301` (D2's master-read line numbers) are off by
   a few lines** as the files stand now — `ContentOpacity` is at `HomeViewModel.cs:301` (correct) but
   the Grid binding is at `HomePage.xaml:406`, not 403. Both were verified by content, not by line
   number, and D3 is satisfied.
3. **D1 asks for strings in `Views/` and `ViewModels/` only**, but the string that stacks hardest —
   the offline banner — is produced in **`Services/HomeCacheFormat.cs`** and merely bound in
   `Views/`. A search restricted to the two named folders would have found the binding and not the
   text. That may be why three attempts missed it.
4. **D2 says "one connection statement" without saying which page owns it on pages that have no
   Phone card.** Home has one; the Sync page cannot, without a new element. Called out under D2.
5. **D4 says "a crude source-text check … in `homelayoutsim` (or the nearest existing harness)"**, but
   the strings that needed pinning also live in `homecachesim`, `synccachesim` and `applaunchsim`,
   which the task does not mention. Three of them broke on the D2 rewording. A task that changes
   user-facing strings should expect every harness that pins one to move.
6. **E2 says "measure the transfer size before and after"** without noting that this is impossible
   without a phone. The honest substitute is documented above; the task should say which of the two
   it wants when no hardware is attached.
7. **Part F's `HomePage.xaml:728` reference** (the `AppsOpacity` dim) is accurate as a pointer to the
   disabled-vs-removed distinction, and the distinction was the right thing to flag — the fix does
   not touch that opacity at all.

## Numbered manual visual test

**Nothing below has been seen by me. `Linc.Desktop` is not running** — I killed it before each build,
as GUARDRAILS requires; your app was live and connected when the session began, so start at step 1.
The Pixel 7 needs the **new debug APK** for Part E: it is built at
`ANDROID/app/build/outputs/apk/debug/app-debug.apk` but **I did not install it** (the task did not
authorise that), so install it yourself before step 7.

### Part D — one connection statement

1. Launch `Linc.Desktop` from
   `Linc/DESKTOP/Linc.Desktop/bin/x64/Debug/net8.0-windows10.0.19041.0/Linc.Desktop.exe`.
2. With the phone **connected**, look at Home. The Phone card should name the phone and say
   *"Connected over …"*. Nothing else on the page should mention the connection.
3. Now **disconnect** (Devices page → Disconnect, or unplug/turn off wireless debugging). Watch Home.
   **Expected: exactly one sentence about the link**, in the Phone card — e.g. *"Pixel 7 / Looking
   for your phone…"*. It should name the phone, **not** say "No phone connected".
4. If a cache exists, the banner at the top should read **"Showing what was last synced at …"** —
   with **no** "Phone disconnected — " prefix. That is the second statement's whole point: it is
   about the cache, not the link.
5. Check the Apps card while disconnected: it should read **"No apps to show yet."**, not
   *"Connect your phone to see the apps installed on it."*
6. Repeat steps 2–5 in the **other theme** (Settings → theme). Nothing should differ.

### Part E — the wallpaper

7. Install the new debug APK on the Pixel 7 and reconnect. (If you would rather not, skip to step 11
   — the desktop side is unchanged in behaviour for an old APK, which is itself worth confirming:
   **an un-updated phone must still show the old soft wallpaper with no error.**)
8. Look at the widgets column on Home. **Expected: the wallpaper is sharp**, not frosted.
9. **Read the text over it** — the widget titles and values, in **both light and dark**. This is the
   one thing I could not check and the reason the dial exists.
10. If any of it is hard to read: open
    `DESKTOP/Linc.Desktop/Services/ThemeSyncService.cs`, find **`ScrimStrength`**, change `0.0` to
    `0.35` (or `0.6`), rebuild. That is the only change needed.
11. Change the phone's wallpaper and confirm the desktop picks up the new one within a few seconds,
    and that the app's accent colour still shifts toward it.

### Part F — Apps off

12. On Home with Apps **visible**, drag the horizontal divider between the tabs panel and Apps to a
    distinctive position (say, Apps quite tall). Let go — that split is persisted.
13. Switch the **Apps** section **off** (the widgets column's 3-dot menu → section visibility).
    **Expected: the Apps card, the gap it occupied, AND the draggable divider all disappear, and the
    Notifications/tabs panel grows to fill the whole column.** No empty band at the bottom.
14. Switch Apps back **on**. **Expected: the divider returns and Apps comes back at the height you
    set in step 12**, not at the default 65/35. This restore path is the subtle half of the change.
15. Switch to your **other phone's tab** and back, with Apps off, and confirm the column stays full.
16. Resize the window narrow and tall with Apps off, and confirm nothing reserves space for it.
