## §2 — verifying the planner's hypothesis

**The hypothesis is correct in substance: the socket is a plain TCP connection the phone dialled,
so its remote endpoint IS the phone's address on whatever interface carried it. It is not
proxied, relayed or NAT'd by anything in Linc.**

**But it is not reachable from where the connect decision is made, and it is not reachable by
any public API from where it is handed out.** Evidence:

1. `TlsTransportService.HandleConnectionAsync` (`TlsTransportService.cs:137`) holds the
   `TcpClient`. That is the only place `Socket.RemoteEndPoint` is live. The client is a local,
   is never stored, and the method ends without the endpoint escaping.
2. What escapes is `ControlArrived?.Invoke(ssl)` (`TlsTransportService.cs:186`) — an
   `event Action<Stream>` (`TlsTransportService.cs:23`).
3. The consumer is `ConnectionSupervisor.OnTlsControlArrived(Stream stream)`
   (`ConnectionSupervisor.cs:338`), which is exactly the connect-decision point: it calls
   `ShouldEngage(LinkTransport.DirectTls)` and then `connection.AdoptTlsConnectionAsync(stream, …)`.
   It has a `Stream` and nothing else.
4. `grep RemoteEndPoint DESKTOP\Linc.Desktop\Services\*.cs` → **no hits anywhere in the desktop.**
5. The obvious workaround does not compile. I built a throwaway console (in scratch, since
   deleted) that tries to walk down from the `Stream`:

   ```
   error CS0122: 'AuthenticatedStream.InnerStream' is inaccessible due to its protection level
   ```

   `SslStream.InnerStream` is `protected`, so a consumer holding only the `Stream` cannot reach
   the `NetworkStream` beneath it, and therefore cannot reach `NetworkStream.Socket.RemoteEndPoint`.
   This is measured, not assumed.

**Smallest change that would expose it** (deliberately NOT made in this task — §6 forbids
restructuring the transport stack, and §3.2's `SelectEndpoint` takes `peer` as a parameter so
nothing in M13a needs it):

> Widen the event to carry what the transport already knows:
> `event Action<Stream>? ControlArrived` → `event Action<Stream, IPEndPoint?>? ControlArrived`,
> and at `TlsTransportService.cs:186` invoke it as
> `ControlArrived?.Invoke(ssl, client.Client.RemoteEndPoint as IPEndPoint)`.
> That is one signature, one call site and one handler signature
> (`ConnectionSupervisor.OnTlsControlArrived`). No type moves, no lifetime changes, and the
> `TcpClient` is already in scope at that exact line. `AwaitChannelAsync`'s dial-back path
> would not need it.

**Two adjacent findings, reported not fixed** (GUIDE.md §3 — do not improve adjacent code):

- **`TlsTransportService.LanAddresses()` will not advertise a Windows-Mobile-Hotspot address.**
  It skips any interface with no IPv4 default gateway (`TlsTransportService.cs:233-238`). When
  the PC hosts the hotspot, that interface *by definition* has no gateway — that is the very
  signal `DecideRole` uses to return `Ap`. So in the PC-is-AP role the mDNS advert will not
  contain the address the phone must dial. The listener itself is fine (`IPAddress.Any`,
  `TlsTransportService.cs:68`), so §3.1's "both sides listen unconditionally" is already
  satisfied; it is discovery that will be blind. **This looks like it will bite M13b/M13c.**
  Measured on this PC: the Mobile Hotspot adapter is `WiFi 5 / 192.168.137.1/24 / gw=(none)` —
  see the probe output below.
- **`ToolLocator.FindAdb()`'s dev-tree candidate climbs six directory levels**, which is right
  for a Debug WinUI build but wrong for a `dotnet run` tool output folder (four levels). From
  `tools/`, `FindAdb()` therefore falls through to the Android SDK copy rather than the repo's
  bundled one. `tools/hotspotprobe` works around it locally with its own walk-up and prints
  which adb it used. Not fixed in production.

## §3 — what was built

### `Services/HotspotRole.cs` (new)

- `enum HotspotRole { Ap, Client }`.
- `HotspotRoleRule.DecideRole(string? gateway, string myAddress)` — pure, no I/O. Null / empty /
  whitespace / `0.0.0.0` / `::` gateway → `Ap`; gateway equal to my own address → `Ap`
  (Windows Mobile Hotspot hosting); anything else → `Client`.
- `HotspotRoleRule.ShouldDial(role)` — only `Client` dials. **There is deliberately no
  `ShouldListen`**: both roles listen unconditionally per §3.1, and `hotspotsim` asserts by
  reflection that no such method has appeared, so a future session cannot make listening
  conditional without tripping a check.
- `HotspotInterfaces.Enumerate()` / `.RoleFor()` — the thin platform wrapper.

**Decision I made** (task left it open): the gateway lookup uses
`IPInterfaceProperties.GatewayAddresses` rather than `GetBestRoute2` or shelling out to
`Get-NetRoute`. It is the same per-interface default-gateway information, in-box, with no
P/Invoke and no process spawn, and `TlsTransportService` already uses it for the same purpose.

### `Services/HotspotAddress.cs` (new)

- `record HotspotInterface(Name, Address, PrefixLength, Gateway, Description, IsVirtual)`.
- `HotspotAddress.SelectEndpoint(peer, announced[], myInterfaces[])` — pure. Order: peer →
  announced → gateway, with peer and announced (both remote-supplied) passed through the
  same-subnet filter and gateways taken from our own adapter config. A link-local IPv6 top
  candidate yields to any IPv4 candidate.
- `HotspotAddress.IsSameSubnet(address, interfaceAddress, prefixLength)` — public so the
  harness tests the filter itself, not only its effect. Non-byte-aligned prefixes handled;
  `/0` rejected outright (it would make every address "local" and defeat the filter).

The `announced` parameter is the M13b hook: **the list is already consumed and filtered here**;
M13b only has to fill it from the `addrs` message. No message type was added this session.

### `Services/HotspotConnect.cs` (new)

`IHotspotConnector` / `HotspotConnector.ConnectAsync(address, expectedSerial, ct)`:

1. `adb disconnect <endpoint>` — **always, before every connect.**
2. `adb connect <endpoint>` — port `5555` hardcoded (`public const int AdbTcpPort = 5555`).
3. All three verifications: output contains `connected to`, `adb -s <endpoint> get-state` is
   exactly `device`, `adb -s <endpoint> get-serialno` equals the expected serial.

Returns a `HotspotConnectResult` record carrying every raw output; it never throws for a connect
failure, because its callers are a diagnostic as often as they are the app. IPv6 literals are
bracketed by `BuildEndpoint`.

**Decisions I made:** (a) it drives `adb.exe` rather than `AdbClient` (which `ConnectionManager`
uses), so the three verifications are literally the three adb commands the task specifies and so
`hotspotprobe` exercises the identical production sequence; (b) it is **not** registered in DI
and nothing in the app calls it yet — the trigger is `adb.announce`, which is M13b.

**Source-address binding: not possible on the adb path, and I did not fake it.** The socket to
the phone is opened by the ADB *server*, not by this process, and adb exposes no interface- or
source-binding control. The one place the API does allow it — a direct reachability probe — does
it, in `hotspotprobe` (§5 of its output shows `from 192.168.1.4`, `from fe80::…%12`).

### `App.xaml.cs` (modified) — the ADB pre-warm

**Checked as instructed: `AdbServerHost.cs` did NOT already do this.** It exposes
`EnsureRunningAsync` and no-ops after the first success, but the only callers were
`ConnectionManager` (both connect paths), `DesktopModeService` and `PairingService` — all of
them on the hot path. Added a small fire-and-forget in `OnLaunched` with its own try/catch (a PC
with no `adb.exe` logs one Info line and carries on). `startupsim` still passes — its source-text
checks are on the three exception handlers sitting above `Services = new ServiceCollection()`,

### `tools/hotspotsim` (new) — pure-logic harness

Compiles the real `HotspotRole.cs` and `HotspotAddress.cs` **verbatim** (D-036 pattern); it owns
no copy of either. `HotspotConnector.ConnectAsync` cannot be called without an ADB server and a
phone, so the ordering is a source-text check **scoped to `ConnectAsync`'s body**, not to the
whole file — a disconnect sitting in some other method would not protect that path (GUIDE.md §4.4).

### `tools/hotspotprobe` (new) — the owner's diagnostic

Compiles the real `HotspotRole.cs`, `HotspotAddress.cs`, `HotspotConnect.cs` and `ToolLocator.cs`
verbatim, so what the owner sees on a real hotspot is what Linc itself would decide.

Read-only with one honest exception, stated in the tool's own banner: if — and only if — TCP 5555
actually accepts a connection, it runs the production connect sequence, because `get-state` and
`get-serialno` cannot be produced any other way. `--no-connect` suppresses even that. It never
runs `adb tcpip`, never touches the firewall, never changes an interface or a route, and writes
nothing to `%LOCALAPPDATA%`. `hotspotsim` asserts that no `tcpip` argument exists anywhere in
`HotspotConnect.cs`.

## §3.5 — three defects the probe found on its first live run

These were in my own code, caught by running the probe against the real LAN rather than by
reasoning about it. All three are fixed and all three now have harness coverage.

1. **The Radmin VPN adapter won the endpoint election.** `SelectEndpoint` originally added
   gateways in enumeration order; on this PC `Radmin VPN` (<vpn-address>/8, gw <vpn-gateway>)
   enumerates before Wi-Fi, so the chosen endpoint was `<vpn-gateway>`. That is exactly the
   "connects leave via the wrong NIC" failure §3.3 warns about, decided one layer above the
   socket. Fixed by ranking physical gateways ahead of virtual/VPN ones — **ranking, never
   rejection**: a virtual gateway is still used when it is the only one. `HotspotInterface`
   gained `IsVirtual`, set by the platform wrapper from a keyword heuristic that extends
   `TlsTransportService`'s list with the VPN family (the Radmin adapter's description is just
   "Famatech Radmin VPN Ethernet Adapter", which the existing list misses entirely).
2. **Link-local IPv6 source binding failed with `AddressNotAvailable`.** Every adapter's
   link-local address is inside `fe80::/64`, so a prefix-bits comparison called Wi-Fi's gateway
   and the VPN adapter's address "same subnet" and bound the probe to the wrong adapter. Fixed
   in the production `IsSameSubnet`: two link-local IPv6 addresses with different scope ids are
   not the same subnet. After the fix the same target answers `ConnectionRefused` from the
   correct source — a real answer instead of a bind error.
3. **A malformed IPv6 dial string in the probe's own display** (`fe80::…%12:5555`). Fixed by
   routing it through the production `HotspotConnector.BuildEndpoint`, which brackets it.

## §7 — task-file issues found

1. **§1's stop-gate and §2's instructions conflict for the case that actually occurred.** §1
   says stop the whole chain "if the desktop's control connection does not expose a usable
   remote endpoint"; §2 says that if the endpoint "is buried where the connect logic cannot see
   it", describe the smallest change and carry on. The measured answer is "the endpoint exists
   and is meaningful, but is unreachable by any public API from the consumer" — which is
   §1's wording and §2's situation simultaneously. **I read §2 as the specific case and §1 as
   covering the general one** (a transport where no meaningful peer address exists at all, e.g.
   a relay), and continued. If the planner meant the chain to stop here, that is my error and I
   would want to know.
2. **§3.3's "bind the source address to the hotspot interface where the API allows" cannot be
   satisfied on the adb path at all** — the socket is opened by the ADB server process, not by
   Linc, and adb exposes no binding control. The clause says "where the API allows", so this
   is not a contradiction, but the task reads as though it were achievable on the connect path.
   Implemented in the probe's reachability check, which is the one place it is possible.
3. **§3.4's probe is described as "read-only" while also being asked to print `get-state` and
   `get-serialno`**, which are only obtainable by running `adb connect`. I resolved it by
   connecting only when TCP 5555 already accepts, stating it in the tool's banner, and adding
   `--no-connect`. Flagging in case the planner meant "never connect".
4. **The `announced` list has no source in M13a.** §3.2 says leave the hook; §3.4 asks the probe
   to resolve a "peer/gateway" address, but the probe has no live TLS control connection to
   read a peer from. I made both `peer` and `announced` optional command-line arguments so the
   owner can feed real values by hand during the test. Worth the planner knowing that step 20
   of the manual script exists for that reason.
