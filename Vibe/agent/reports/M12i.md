## A2 — staleness guard (packagesim check 10/10)

Added to `tools/packagesim/Program.cs`. Design, as specified:

- **Compares:** the newest of `Linc.Desktop.{exe,dll,pdb,pri}` in the publish output, against the
  newest `*.cs` / `*.xaml` / `Linc.Desktop.csproj` under `DESKTOP/Linc.Desktop/` (excluding
  `bin/`, `obj/`, `Generated Files\`). I anchored the "publish timestamp" to the app's own rebuilt
  artifacts specifically — not a whole-directory max — because vendored content (scrcpy, VC++
  redist, WindowsAppSDK DLLs) keeps its original mtime when copied and would make a stale publish
  look artificially fresh if included.
- **Does not** touch `tools/` or `ANDROID/` — matches A2's design note exactly.
- **Tolerance: 2 minutes.** Chosen as a small, round grace period per the task's "a minute or two."
- **Missing publish → SKIP**, same pattern as checks 8-9, never a fail — implemented and verified
  (see check 10's `else` branch structure; this mirrors checks 8/9's own `if (!Directory.Exists...)`
  skip).
- **Failure message names both timestamps and the offending file** — verified live in the negative
  proof below.

**A3 — what this guard proves and does not prove**, as required: **it proves the publish is not
older than the code.** It does **not** prove the publish is *correct* — that's checks 1-9's job
(payload presence, `.pri` wiring, adb path, VC++ redist). A stale-but-otherwise-broken publish
would still fail checks 1-9; a fresh-but-broken publish (e.g., a payload accidentally deleted from
source) would still fail those same checks. Check 10 closes one specific, previously-uncaught gap:
a publish that is *structurally complete but generationally behind the code that's supposed to be in it*.

# PART B — `canSleep`

## Modern Standby hypothesis — CONFIRMED, with one correction

The task's field name is wrong. I checked the real `SYSTEM_POWER_CAPABILITIES` struct against
this machine's Windows SDK header (`C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\um\winnt.h`):
**there is no field named `SystemS0LowPower`.** Modern Standby / S0 low-power idle is exposed
through the field named **`AoAc`** ("Always On, Always Connected" — Microsoft's original name for
the same capability, later marketed as Modern Standby / InstantGo / Connected Standby). I used
`AoAc`. See "Ambiguous/wrong" below.

**B1.** Declared `SYSTEM_POWER_CAPABILITIES` with `[StructLayout(LayoutKind.Explicit, Size = 76)]`
in `PcControlService.cs`, naming only the two fields needed at their real byte offsets computed
from the header (`SystemS3` at offset 5, `AoAc` at offset 20; `Size = 76` matches the full native
struct so `GetPwrCapabilities` writes into a correctly-sized buffer without this type declaring
every one of the struct's other ~30 members). `GetPwrCapabilities` (`powrprof.dll`) added as a new
`DllImport`. `canSleep` in `BuildStatePayload` now calls a new `TryGetCanSleep()` which calls
`GetPwrCapabilities` and feeds both flags to `PcPowerCapabilities.CanSleep`. **Removed**
`IsPwrSuspendAllowed()` — its only caller was the old `canSleep` line, and per the task it's the
thing being replaced; leaving it declared and unused would have added a dead P/Invoke and (likely)
an IDE0051 warning. `canShutdown` still uses `IsPwrShutdownAllowed()`, untouched.

**One nuance worth flagging, not acted on:** `GetPwrCapabilities`'s `SystemS3` reports hardware
*capability* only — it does not reflect a live Group Policy lock the way `IsPwrSuspendAllowed()`
did. Following the task literally (use `GetPwrCapabilities` for both signals) means a machine
whose S3 hardware exists but is policy-blocked would now report `canSleep: true` on legacy
hardware where it previously (correctly) reported `false`. On a Modern Standby machine like this
one, `AoAc` dominates and this doesn't matter. I implemented what the task asked for; flagging the
edge case in case it matters for a machine this dev box can't represent.

**B2.** `TryGetCanSleep` and `GetPwrCapabilities` are read-only — a struct query, nothing else.
No new code path can suspend the machine. `SetSuspendState` (the actual sleep call) is unchanged,
still only reachable from the existing `Execute("sleep", ...)` branch gated by
`PcControlValidator`.

**B3.** New file `DESKTOP/Linc.Desktop/Services/PcPowerCapabilities.cs` — zero P/Invoke, one pure
static method: `CanSleep(bool s3Allowed, bool s0LowPower) => s3Allowed || s0LowPower`. Added to
`tools/pccontrolsim/pccontrolsim.csproj` as a `Compile Include` (same posture as
`PcControlValidator.cs`) and exercised in a new pccontrolsim section 6 over all four flag
combinations, calling the **real** production method — not a model of it. `pccontrolsim`'s section
1 (the P/Invoke-metadata scan of the harness's own assembly) still passes with this file included,
confirming it really is P/Invoke-free.

**B4.** Verified with the M4b throwaway-console-outside-the-repo + reflection pattern, then
deleted:

- Built a scratch console at
  `.../scratchpad/m12i-canSleep-probe/` (outside the repo) that compiled
  `PcControlService.cs`, `PcPowerCapabilities.cs`, `PcControlValidator.cs`, and `Envelope.cs`
  **verbatim** (`Compile Include` from their real repo paths), plus a hand-written `Stubs.cs`
  giving only the two interface members (`IConnectionManager.CompanionMessageReceived`,
  `.SendToPhoneAsync`, `ILogService.Log`) `PcControlService.cs` actually references, so the file
  type-checks without pulling in the real (huge, out-of-scope) `ConnectionManager`/`LogService`.
- Called `PcControlService.GetPwrCapabilities` and the private static `TryGetCanSleep` by
  reflection — real production code, no model.
- **Result on this machine:**
  ```
  GetPwrCapabilities() returned: True
    SystemS3 (legacy ACPI S3) = False
    AoAc (Modern Standby / S0 low-power idle) = True
  TryGetCanSleep() [real production method] = True
  PcPowerCapabilities.CanSleep(False, True) [pure fn, same inputs] = True
  ```
  `SystemS3 = False` is consistent with M4b's earlier finding that `IsPwrSuspendAllowed()`
  returned `false` here. `AoAc = True` confirms this is a Modern Standby machine. **`canSleep` now
  correctly reports `true`**, matching the fact that Sleep works from this machine's own Start
  menu — the bug the task exists to fix.
- Deleted the entire scratch directory afterward; nothing under it was ever part of the repo.
  `git status` from `Linc/` shows no trace of it (confirmed above).
- **No sleep/shutdown/lock/restart was ever invoked** — only the read-only capability query.
