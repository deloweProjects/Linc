## §2 — self-arming

### 2.1 Where the one-time grant went

**`PhoneSetupService.GrantAllAsync` — the existing post-install grant pass, extended, not
duplicated.** It already runs `cmd notification allow_listener`, eight `pm grant`s and an
`appops set` immediately after `InstallCompanionAsync` uploads the APK over the ADB session
onboarding already holds. The self-arm grant is now the last entry in that same plan:

```
pm grant app.linc.android android.permission.WRITE_SECURE_SETTINGS
```

**No second ADB path was built.** D-001 holds: the user never sees ADB or a terminal, because
this happens inside the install they were already doing.

**It is last in the plan on purpose.** It is the newest and least essential of the grants, so a
phone whose OEM refuses it still received every grant before it.

**Manifest.** `WRITE_SECURE_SETTINGS` is `signature|privileged`, so `pm grant` fails outright
unless the app declares it. Added to `AndroidManifest.xml` with `tools:ignore="ProtectedPermissions"`
and a comment saying plainly that **declaring it grants nothing** — a normal install leaves it
ungranted, and only the onboarding `pm grant` makes it held.

**Idempotent and never fatal — restructured so that is provable.** The plan and the loop that
runs it moved into `PhoneSetupCommands` (pure, no `AdbClient`, no phone). `RunPlanAsync` catches
per command, records the failure, and **carries on to the next one**; it never rethrows.
`GrantAllAsync` now calls exactly that. `tools/hotspotsim` runs the **real** `RunPlanAsync` with a
runner that throws on the self-arm command and asserts every other command still ran — see §4.5.
That is the seam that turns acceptance item 5 from a claim into a check.

**UI surfacing (disable, don't hide).** A permanent "Instant hotspot link" section on the phone's
Settings screen, greyed rather than hidden when the grant is missing, saying:

> This phone hasn't given Linc permission to turn wireless debugging on by itself. Turn it on in
> Developer options when you want an instant hotspot link.

and when granted, either "Ready. Wireless debugging is on, so your PC connects the moment you
share a hotspot either way." or "Ready. Linc will switch wireless debugging on for you when your
PC asks." **There is deliberately no toggle** — arming happens when the desktop asks over the
protocol, not from a switch that silently changes the device. The desktop side records
`IPhoneSetupService.SelfArmGranted` and logs the plain-language reason when the grant did not land.

**One honest caveat about `SelfArmGranted`:** `pm grant` reports a refusal by writing to stderr
rather than by failing, so on a phone that blocks the permission this flag can still read true.
It is an optimistic signal for explaining a missing feature, not proof the permission is held —
the phone re-checks for real before every write. Documented in the property's own doc comment.

### 2.2 Arming, phone side

`service/AdbArming.kt` + the pure `AdbArmRules` in `AdbLinkRules.kt`:

```kotlin
Settings.Global.putInt(context.contentResolver, "adb_wifi_enabled", 1)
```

Guarded exactly as asked: `AdbArmRules.plan(hasPermission, currentlyEnabled)` decides **before**
anything is written — no permission → `DENIED`, already on → `ALREADY_ON` (writes nothing), else
`ARMED`. `SecurityException` is caught and reported as `UNAVAILABLE`; nothing escapes into the
control loop.

**It never turns wireless debugging off.** There is no disarm path, and a unit test asserts it by
reflection: no method on `AdbArmRules` whose name contains "disarm" or "disable", and the only
value any outcome writes is `1`.

**Trigger:** `adb.arm` from the desktop → arm → re-run detection (M13b §2.2) → verify (M13b §2.3)
→ announce. Wired through a new `onAdbArm` lambda kept **separate from** `announceAdb`, so the
handshake path can never arm on its own — arming is a visible change to the user's device and
only happens when the desktop explicitly asks.

Boot → arm → discover → verify → announce works because TLS pairing state survives a reboot, so an
already-paired PC needs no QR and no interaction. **That sequence has not been observed; it is the
design, wired.**

### 2.3 Promotion to a fixed port

`Services/HotspotPromotion.cs` — `adb -s <endpoint> tcpip 5555`, run **only after** a verified
link is already up, and only when the phone announced some other port. Never used to establish a
link. It does not survive a reboot, and the class doc says so in those words.

**This inverts something M13a's harness asserts, and I did not weaken the assertion.** M13a's
`hotspotsim` check *"no code in `HotspotConnect.cs` arms the phone — there is no 'tcpip' argument
anywhere in it"* was written when arming was out of scope. M13c adds arming as a deliberate
capability. Rather than relax that check to force a pass (GUIDE.md §4.5), **promotion went into a
separate file**, so:

- the M13a guarantee still holds **verbatim** — the connect path still cannot arm anything;
- the new capability has its own checks: it lives in `HotspotPromotion.cs`, it always passes
  `-s <endpoint>` (an unqualified `tcpip` would hit whichever phone adb felt like), and it is only
  called after a verified link.

`adb tcpip` was never executed this session. It runs only when a caller passes a live endpoint,
and there was no device.

## §3 — the race, the health loop, the keepalive, the instrumentation

### 3.1 The speculative race

`HotspotLinkService.StartSpeculative()` fires an optimistic connect at
`SelectEndpoint(peer, null, interfaces)` — peer-or-gateway — without waiting for an announcement.
The announced branch runs the same `AttemptAsync`. First success wins; the winner cancels the
loser's `CancellationTokenSource`; the loser stands down without disconnecting the winner's link.

**Both branches go through the full verify.** There is one attempt method, and the claim is
`race.TryClaim(branch, result.IdentityVerified)` — the connector's own verdict, which is
`get-state == device` **and** `get-serialno == expected`. `HotspotRaceState.TryClaim` returns
`RejectedUnverified` for an unverified branch and **leaves the race open**, so a fast-but-anonymous
connect cannot win and cannot block the branch that does verify. A 64-way concurrent claim test
asserts exactly one winner.

The announce handler no longer holds the service gate across the connect — it releases after the
generation bookkeeping — or the two branches would have been sequential and there would have been
no race at all.

### 3.2 The health loop

Polls `adb devices` every **4 s** (`HotspotBackoff.PollInterval`; the spec's window is 3–5 s).
On anything other than `device`: back off, then **`adb disconnect <endpoint>` before re-resolving**,
then reconnect through the same verified path.

`HotspotBackoff.DelayFor` is pure and fully tabulated by the harness: 250 ms, 500 ms, 1 s, 2 s,
4 s, 8 s, 15 s, 15 s… including at `int.MaxValue`, where a naive doubling would have overflowed
into a tiny delay. `HotspotBackoff.ShouldReset` resets on a verified success **and** on any `gen`
increment — a new link event means conditions genuinely changed, so the next attempt is eager
rather than penalised for the old topology's failures. A new generation also opens a fresh race.

### 3.3 Keepalive — checked, and nothing changed

**`ConnectionSupervisor` already does this. I changed nothing.**
`HealthInterval = TimeSpan.FromSeconds(15)` (`ConnectionSupervisor.cs:86`) and
`HealthLoopAsync` (`:454`) sends `connection.GetStatusAsync(ct)` over the control socket every
15 s for as long as the link is Connected. That is real traffic on the control socket at a
low rate — exactly the SoftAP keepalive §3.3 describes, and the app link does count as a client.
No second keepalive was added; a second one would have been duplicate traffic for no gain.

**Not verified:** that 15 s is actually short enough for every Android build's SoftAP idle timer.
The 5–10 minute figure in the task file is comfortably longer than 15 s, so it should hold, but
this has not been measured on this hardware.

### 3.4 Per-stage instrumentation

`HotspotStageTimer` records each stage's elapsed ms and emits **one** greppable line. Marks:

| Stage | Marked at |
|---|---|
| `resolve` | announcement admitted → endpoint chosen (parse, gen check, `verified` check, serial check, same-subnet filter) |
| `adb connect` | `HotspotConnector.ConnectAsync` returned |
| `verify` | `get-state`/`get-serialno` classified, including the one `offline` retry |

Example log line shape:
`Wireless debugging is up at 192.168.43.1:5555 via the announced attempt - resolve 3 ms, adb connect 118 ms, verify 41 ms = 162 ms total`

Past 1.5 s (`HotspotStageTimer.SuspiciouslySlow`) the same line appends *"over 1500 ms — something
is scanning; the stage above with the large number is the one to look at"*. The phone side already
logs its own detection method and port (M13b), which covers the port-discovery stage.

**The link-up → app-link stage is not instrumented.** It starts before any Linc code runs on
either side (Wi-Fi association, DHCP, then the phone's presence loop dialling out), so the desktop
cannot time its beginning. Flagged rather than faked with a number that would start at the wrong
moment.

## §5 — THE COMBINED MANUAL TEST SCRIPT

**This is the whole point of the chain. Until it is run, nothing here is known to work.**

Everything below needs phone taps and a hotspot — both forbidden to me, both yours. Paste each
`hotspotprobe` output back verbatim; the failures are usually visible in it.

### Part 0 — once, with a cable (this is also the self-arm test)

1. Open a terminal at `Linc`.
2. Plug the Pixel 7 in over USB. Confirm with
   `SCRCPY\Linc.scrcpy\bin\adb.exe devices` — you want one `device` line, not `unauthorized`.
3. Launch the desktop app and run onboarding (Settings → re-run setup) so it reinstalls the
   companion. **This is what performs the one-time `WRITE_SECURE_SETTINGS` grant.**
4. Verify the grant landed:
   `SCRCPY\Linc.scrcpy\bin\adb.exe shell dumpsys package app.linc.android | findstr WRITE_SECURE_SETTINGS`
   — you want a line ending `granted=true`. **If it says `granted=false`, say so and stop here for
   Part 3** — everything else still works, but self-arming will not, and the phone's Settings
   screen should be showing the greyed "Instant hotspot link" row explaining exactly that.
5. On the phone, open Linc → Settings and read the **Instant hotspot link** row. Paste what it
   says. It must be present either way — if it is missing entirely, that is a bug.
6. Unplug the USB cable.

### Part 1 — phone hosts the hotspot, PC joins it

7. On the phone, turn the Wi-Fi hotspot on.
8. On the PC, join that hotspot from the Wi-Fi flyout. Windows may ask whether the network should
   be discoverable — **note what you answer**; it decides Public vs Private.
9. Run `dotnet run --project tools/hotspotprobe` and paste the whole output.
10. **Good looks like:** in `[1]`, the Wi-Fi row shows role `CLIENT` with the phone as its gateway.
    In `[4]`, `chosen:` is that gateway (or the phone's address). In `[5]`, TCP 5555 says
    `ACCEPTED` in **under ~100 ms**. In `[6]`, `get-state` is `device`, `get-serialno` is
    `<your-device-serial>`, and `identity ok : True`.
11. **Bad looks like:** `[2]` shows the hotspot interface as `category=Public` with the warning
    block. That is the single most likely cause of "the phone just isn't there" — paste it if it
    appears. Also bad: `[5]` shows ~3000 ms and `no` — that is a timeout, meaning adbd is not
    listening on 5555 at all (expected if step 15 has not run yet).
12. Open Linc on the PC → Logs, and look for a line like
    `Wireless debugging is up at <ip>:5555 via the announced attempt - resolve N ms, adb connect N ms, verify N ms = N ms total`.
    **Paste that line — the per-stage numbers are the measurement the planner asked for.** Target
    is ~150–300 ms total. Anything over 1.5 s appends a warning naming the slow stage.
13. On the phone, open Linc → Logs and paste the last few lines. You are looking for
    `Told the PC where wireless debugging is listening (port NNNN, <how it was found>)` — **the
    "how it was found" part tells us which of the three detection methods actually works on a
    Pixel 7**, which nothing in this chain could determine.
14. **On the phone, open Developer options: is *Wireless debugging* still togglable while the
    hotspot is on, or greyed out?** Say which. This one answer decides whether self-arming is even
    possible on this device.
15. If nothing had 5555 open: with the cable back in, run
    `SCRCPY\Linc.scrcpy\bin\adb.exe tcpip 5555` once by hand, unplug, and repeat from step 9. That
    is the manually-armed path M13a assumes; it lasts until the phone reboots.
16. `SCRCPY\Linc.scrcpy\bin\adb.exe devices` — paste it.

### Part 2 — Windows Mobile Hotspot on, phone joins it

17. Turn the phone's hotspot off; disconnect the PC from it.
18. PC: Settings → Network & internet → Mobile hotspot → on.
19. On the phone, join that hotspot from the Wi-Fi list.
20. Run `dotnet run --project tools/hotspotprobe` and paste the whole output.
21. **Good looks like:** in `[1]`, the row holding `192.168.137.1` (the `WiFi 5` adapter on this
    PC) shows `AP -> listen only` with `gw=(none)`. That is correct — when the PC hosts, there is
    no gateway to dial.
22. **`[4]` is the interesting one.** I expect `chosen:` to say
    *"nothing survived the same-subnet filter"* or to name the wrong LAN gateway, **because in
    this role the phone's address can only come from the control socket's peer address or from
    `addrs`, and the probe has neither.** Whatever it prints, paste it — it tells the planner
    whether the announce message is required or merely convenient in the PC-as-AP direction.
23. Re-run with the phone's address passed in once you can see it (phone → Wi-Fi → the hotspot →
    IP address): `dotnet run --project tools/hotspotprobe -- 192.168.137.x` and paste that too.
24. `[2]` again: is the Mobile Hotspot interface Public? Paste the warning if it appears.
25. Check the PC's Logs page for the timing line as in step 12, and the phone's Logs as in step 13.
26. Again: is *Wireless debugging* still togglable on the phone in this direction?
27. `SCRCPY\Linc.scrcpy\bin\adb.exe devices` — paste it.

### Part 3 — the self-arm round trip (only if step 4 said `granted=true`)

28. On the phone, turn *Wireless debugging* **off** in Developer options.
29. Bring up either hotspot again and let the PC and phone connect.
30. On the phone's Logs, look for `Turned wireless debugging on for the PC.` **If that line
    appears, self-arming works** — that is the "cable disappears" result and the single most
    valuable outcome of this chain.
31. If instead you see *"This phone hasn't given Linc permission…"*, the grant did not stick;
    paste it and re-check step 4.

### Anything you want to measure without touching adb state

`dotnet run --project tools/hotspotprobe -- --no-connect` — measures and prints, never connects.

## §6 — what I could NOT verify

**Across all three milestones:**

- **Any of this working over a real hotspot. No hotspot was brought up in any of M13a, M13b or
  M13c. Nothing in these three reports is evidence that the feature works.** No `adb.announce` has
  ever left a phone, no `adb.ack` has reached one, no ADB link has come up over a hotspot segment,
  and the ~150–300 ms target is the planner's number, not a measurement.
- **Every `android.*` path.** `SystemProperties` reflection, `NsdManager` browse/resolve, the
  loopback liveness connect, `Settings.Global.putInt`, and the permission check all compile and
  are wired, and the rules they apply are unit-tested — but none has been observed executing on a
  device. The 400 ms NSD budget is a chosen number, not a measured one.
- **The `WRITE_SECURE_SETTINGS` grant actually landing on a Pixel 7.** The plan is proven, the
  manifest declares it, the failure path is proven non-fatal — whether the OEM permits it is step
  4 of the manual script.
- **`adb tcpip 5555` promotion.** Never executed. Deliberately: acceptance §8 forbids it.
- **The speculative race under real timing.** The claim rule is proven, including under 64-way
  concurrency, but no branch has ever raced a real one; which branch usually wins is unknown.
- **The health loop's recovery.** No link has ever dropped, because none has ever come up.
- **§2.2 method 3's ephemeral sweep** — deferred in M13b (arithmetic there), so it is untested
  because it does not exist. **The consequence: on a phone where the system properties are unset
  AND NSD fails, wireless debugging on a random TLS port will not be found.**
- **The keepalive claim.** The existing 15 s ping is confirmed present in code and unchanged; that
  15 s is short enough for every Android SoftAP idle timer is reasoning, not measurement.
- **The new phone Settings row's appearance.** It compiles into the APK; it has not been rendered.
- **The desktop app was never launched** in any of the three milestones. All DI registrations and
  `Attach()` calls compile and follow the existing `pcControl` pattern, but no process was started
  to observe them, and `hotspotLink.Attach()` has never run.
- **`unauthorized` → pairing** routes to a log line and a hard "do not retry", not to the pairing
  UI. Flagged in M13b, unchanged.
- **`syncsim`'s flake** — reported honestly in §4.4 rather than resolved; out of scope.

## §7 — issues found in this task file

1. **§2.3 inverts M13a's harness assertion.** M13a's `hotspotsim` asserts no `tcpip` argument
   anywhere in the connect path; M13c §2.3 adds `adb tcpip 5555`. Resolved by putting promotion in
   its own file so the M13a guarantee survives verbatim, per GUIDE.md §4.5. Worth the planner
   knowing the two files were written three hours apart with opposite requirements.
2. **§2.1's "surface the resulting capability honestly in the UI" does not say which UI.** The
   phone is the only side that can check the permission for real, so the row went on the phone's
   Settings screen; the desktop's `SelfArmGranted` is optimistic (see §2.1). If the planner meant
   a desktop-side row, that is not built.
3. **§3.4 asks for a "link-up → app link" timing the desktop cannot take.** That interval starts
   before any Linc code runs on either side. Every other stage is instrumented; this one is
   flagged rather than faked.
4. **§3.1 says "fire an optimistic connect at the best guess (`peer-or-gateway:5555`)" but does
   not say what triggers it.** `StartSpeculative()` is exposed on `IHotspotLinkService` and nothing
   calls it yet — there is no "link-up" event on the desktop that is distinct from the control
   connection arriving, and hooking it into `ConnectionSupervisor`'s TLS-adopt path would have
   meant touching the transport ranking, which §6 forbids. **The race is built and proven; its
   trigger is one line that a later milestone (or an amendment) should place.** Reporting rather
   than silently wiring it somewhere plausible.
5. **M13b's spec corrections still stand** and are not repeated here: PROTOCOL.md's "lower than"
   vs "equal-or-stale" for `gen`, and `serial` needing to be optional on the wire. Both are in
   `Vibe/agent/reports/M13b.md` §5 and neither is fixed, because I do not edit `.md` files other
   than these reports.
