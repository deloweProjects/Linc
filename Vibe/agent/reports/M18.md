## 4. PART B — dynamic colour, and the contrast floor
**B1** — new `Services/DynamicPalette.cs` (pure, no WinUI) derives the tonal roles from the wallpaper's dominant colour.
New setting **"Use my phone's colours", default ON** (`UsePhoneColours` on `DeviceRegistry`, Appearance card on the
Settings page). **The fallback is not a branch:** setting-off, phone-disconnected and no-wallpaper all reach the same call
with a null dominant, which returns the M14 neutral ramp *exactly*.

**B2 — the task's premise here is out of date, and I did not follow it.** It says the phone uses
`dynamicLight/DarkColorScheme` on API 31+ and asks me to make the *fixed* scheme match the desktop. **M17a already removed
dynamic colour from the phone's UI entirely** — `Theme.kt` now has one neutral scheme on every API level, and its comment
says so. Restoring the dynamic path would regress M17a and re-break the "one product" look, so I left it. **B2's actual
goal is already met and I verified it byte-for-byte:** `Color.kt`'s values are identical to `MaterialExpressive.xaml`'s.
That check also caught a mistake of my own — my first `DynamicPalette` constants were invented (`#FAFAFC` etc.); I
replaced them with the real shipped values, so `palettesim`'s "fallback == base state" check tests reality, not a fiction.

**B3 — THE CLAMPING RULE:** *tint the neutral surface toward the wallpaper's dominant colour by at most `MaxTint` (0.14);
then, while the result fails the required ratio against the theme's body-text colour, walk the surface back toward the
theme's own extreme (white in light, black in dark) in `ClampStep` (0.05) increments until it passes.* It always
terminates on a passing colour, because white-against-dark-ink and black-against-light-ink both clear the floor by a wide
margin — so a dark wallpaper cannot produce grey-on-grey, it just produces a less tinted surface. The muted caption
colour is clamped separately against the surface it actually sits on.

**WORST-CASE MEASURED, by sweeping the full RGB cube at step 17 in BOTH themes — 8,192 wallpaper/theme combinations:**
| | worst ratio | at wallpaper | floor |
|---|---|---|---|
| body text (`onSurface` on surface and on card) | **8.57:1** | `#FFFFFF`, dark | 4.5:1 |
| caption text (`onSurfaceVariant` on surface) | **5.64:1** | `#000000`, light | 4.5:1 |
| neutral ramp's own body contrast | 18.21:1 light / 17.43:1 dark | — | 4.5:1 |

**Zero breaches.** `palettesim` also checks the ratio function itself against WCAG's published reference values (black on
white 21.00, mid-grey on white 3.95, blue on white 8.59) so the sweep is not resting on wrong maths, and bounds the tint
(worst surface drift 14.1% from neutral, ceiling 35%) so dynamic colour cannot repaint the app.

**B4 — no flicker.** `ApplyWallpaperAccent()` mutates the `Color` of brushes that are *already in the resource dictionary
and already bound*. Nothing is re-created, no view model is re-constructed, and `Wallpaper` is not touched on that path,
so a palette change cannot flash white or drop the wallpaper for a frame. The setting change re-derives immediately via
`UsePhoneColoursChanged` rather than waiting for the next 15 s status. **Reasoned from the code, not observed** — I did
not drive the desktop UI.
