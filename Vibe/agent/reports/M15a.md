### A2 — the hypothesis, verified and disproven

**Untargeted calls: 6 of 31, and all six are `adb devices` / `start-server` / `restart-server`.**
Every one already carries an explanatory comment or is self-evidently global. **No adb call in the
onboarding, pairing or device-add path lacks a device selector.** Nothing needed retargeting, so
A2's code change is **not made** — there was nothing to change.

The owner's `error: more than one device/emulator` is real, but it came from **their own terminal**
running a bare `adb tcpip 5555`, not from Linc: Linc's own `tcpip` is
`HotspotPromotion.cs:54`, which has carried `-s <endpoint>` with a comment saying why since M13e.

**So why does a second phone never produce the trust prompt?** Reading the enclosing blocks
turned up two silent filters, and together they account for the symptom exactly:

1. **`UsbWatcherService`'s poll dropped every non-`Online` device.** The loop's single condition
   was `device.State == DeviceState.Online && !HostPortPattern.IsMatch(device.Serial)`. A phone
   whose trust prompt is pending reports **`unauthorized`**, so it failed that test and was
   discarded without a word. `ConnectionManager.EnsureOnline` has had a good `unauthorized` message
   since M2b — but it is only reached on a **connect attempt**, and no connect is ever attempted
   for a device the watcher never reports. The state was invisible end to end.

2. **`ConnectionSupervisor.OnUsbDeviceSeen` returned in silence for any unknown phone whenever a
   link was live.** The guard was `if (State is not (LinkState.Searching or LinkState.NoDevice)) return;`
   — so with the first phone connected, a second phone that *was* authorised still produced no
   confirmation card, no message, nothing. `DeviceViewModel.ShowUsbDeviceDetected` is additionally
   gated on `IsDisconnected`, so even the card could not have shown.

**A caveat I want on the record, because it limits what any fix here can promise:** the *"Allow USB
debugging?"* dialog is drawn by **adbd on the phone**, triggered by the ADB server's connection
attempt. Linc cannot make it appear. What Linc controls — and what was broken — is whether the
resulting `unauthorized` state is ever shown to the user. If the prompt genuinely never appears
even with the phone unlocked, the remaining causes are on the phone (a revoked/absent RSA key, or
"Revoke USB debugging authorisations" needing a tap), and the fix below at least *says so* instead
of leaving a blank screen.

### A5 — two phones at once: the honest answer

**D-037 stands. Concurrent live links were not built.** What changed is that the limit is visible
and graceful:

- `DeviceAdmission.DecideDeviceSwitch(current, requested, currentState)` — a pure static, exactly
  the signature the task named. Returns `Connect` / `SwitchAfterDisconnect` / `AlreadyConnected` /
  `Refuse`, each with a plain-language sentence. **It can never return `Connect` while a different
  phone is live** — that outcome is what two concurrent links would look like from this function,
  and it is what negative proof (b) breaks.
- The supervisor routes every unknown phone through it. A second phone while one is connected now
  gets a message *and* the confirmation card, instead of a silent `return`. Activating the card
  calls `ConnectUsbManualAsync`, which tears the first link down before bringing the second up.
- `currentState` is a small pure `LinkActivity` enum rather than `LinkState`, because `LinkState`
  lives in `ConnectionSupervisor.cs` which drags in `AdvancedSharpAdbClient` and `Microsoft.Win32`
  and cannot link into a net8.0 harness. The mapping is one switch at the single call site. **This

| Stage | Trigger in code | Latency |
|---|---|---|

### The slow stage is **stage 4**, and it was unbounded

After `OnLinkDropped()` the supervisor sits in `Searching`. The only things that start a wireless
reconnect are an mDNS `ConnectServiceSeen` advert, a BLE sighting (which merely calls `ScanNow`), a
`NetworkAddressChanged`, a power resume, or a connection-preference change. **Pulling a USB cable
raises none of them.** `RecoverPresentWirelessDeviceAsync()` — the one path that adopts a phone the
ADB server *already holds* — was wired to resume, network change and preference change, but **not
to a link drop.** So the link stayed down until the phone happened to re-advertise.

**This is why M13f looked right and the symptom survived.** M13f fixed *which* transport wins when
both are candidates. After a USB drop there is no wireless candidate offered at all, so ranking
never gets a turn. Ranking was never the bottleneck.

**Answering the task's two hypotheses directly:** the 15 s poll is a **real but bounded** floor
(stage 2, 6–21 s) and is *not* the dominant term. The stale-adb-entry hypothesis is **unverified** —
it needs a phone. The dominant term was neither.

### The fix, and its limits

`OnLinkDropped()` now ends with `discovery.ScanNow(); _ = RecoverPresentWirelessDeviceAsync();` —
the same bounded, single-flighted pair already used by resume, network change and preference change.
A drop is at least as strong a signal as any of those. It is small, adds no timer, changes no
constant, and reuses machinery that has been in production since M4.

**I did not change the 15 s health interval.** Per the task's own instruction: that is stage 2, it
is bounded, and lowering it costs battery and adds reconnect churn during mirroring (the reason the
3-consecutive-failures rule exists at all). **Changing the poll interval belongs in its own
session, with a phone attached to measure stage 1 first** — without stage 1's number there is no way
to know whether a faster poll would even help.

Stage timings are now **logged in production**: each failed probe logs its position in the streak
and elapsed ms, and `OnLinkDropped` logs total detection time from the first failed probe. The next
real cable pull produces the numbers from the owner's own log with no instrumentation run.

## PART C — let the user just pick wireless

> *Result line, written on finishing Part C:* pure static + supervisor state + UI, harness-proven
> with no hardware.

- `TransportRank.ChooseWithOverride(candidates, manualOverride)` → `TransportChoice(Name, ByHand,
  OverrideDropped)`. A hand-picked transport beats the ranking, **but only while it is answering** —
  honouring a dead one would reinstate exactly the bug M13f fixed. When it cannot be honoured the
  result falls back to the automatic pick **and says so** via `OverrideDropped`.
- `ConnectionSupervisor` gains `ManualTransport`, `TransportChosenByHand` and
  `SetManualTransport(LinkTransport?)`. Picking a transport acts immediately (`ScanNow` +
  `RecoverPresentWirelessDeviceAsync`) rather than waiting for the next event. `ShouldEngage`
  refuses every other transport while one is pinned, so nothing can take the link off it.
- **The override never dies silently.** `ClearManualTransport(reason)` raises a user-facing message
  and logs. It fires from two places: `ChooseWithOverride` reporting a dropped override, and
  `OnLinkDropped` when the pinned transport is the one that died.
- UI: `Views/DevicePage.xaml` gains a *"Use this link now"* card — **Use wireless now**, **Use USB
  now**, **Back to automatic** — and the Link tile now shows a second line, **"chosen by you"** or
  **"chosen automatically"**, so the page says both *which* transport and *who decided*.

This is deliberately **not** the existing per-device `ConnectionPreference` dropdown: that is sticky
policy that forbids other transports permanently, whereas this is a session override that falls back
and announces itself when its transport dies.
