## §1 — the gate, and the judgement call it forced

> "STOP THE CHAIN and report if M13a's §2 verification failed — if the control socket's peer
> address is not reachable from the connect path…"

**M13a measured this precisely: the peer address exists and is meaningful, but was NOT reachable
from the connect path.** `ControlArrived` handed out a bare `Stream`, and
`AuthenticatedStream.InnerStream` is `protected` (compile-verified, `CS0122`), so there was no
public route from the consumer back to the socket.

**I did not stop. I made it reachable, and I am flagging that as the most important thing in this
report.** The reasoning:

- The blocker was one signature wide, not a design flaw. `TlsTransportService.HandleConnectionAsync`
  already holds the `TcpClient` at the exact line that raises the event.
- M13a's §2 explicitly anticipated this outcome and asked me to *describe the smallest change*.
  I described it in M13a's report; M13b then needs it, because §2.4 says "resolve via M13a's
  `SelectEndpoint`" and `SelectEndpoint`'s first-priority input is the peer address.
- M13b's §5 out-of-scope list does not carry M13a's "do not restructure `TlsTransportService`".
- GUIDE.md §3 permits an unasked-for change "when the task cannot be completed correctly without
  it… then do it, and flag it explicitly as unasked-for". This is that case.
- The gate's stated rationale — "the announce protocol has nothing to attach to" — does not
  actually hold: `adb.announce` attaches to the companion message stream, and `addrs` exists
  precisely so the peer address is not required. So a strict stop would have been a stop on a
  premise the spec itself contradicts two paragraphs later.

**The change, exactly as M13a's report predicted it:**

```csharp
// TlsTransportService.cs
- event Action<Stream>? ControlArrived;
+ event Action<Stream, IPEndPoint?>? ControlArrived;
- ControlArrived?.Invoke(ssl);
+ ControlArrived?.Invoke(ssl, client.Client.RemoteEndPoint as IPEndPoint);
```

plus the two signatures it forces (`ConnectionSupervisor.OnTlsControlArrived`,
`IConnectionManager.AdoptTlsConnectionAsync`) and one new read-only property,
`IConnectionManager.PeerAddress`. No type moved, no lifetime changed, no transport ranking touched.
`PeerAddress` is populated for Direct TLS only and cleared in `Disconnect()`.

**`PeerAddress` is deliberately null on ADB links.** An ADB control socket is a loopback forward,
so its peer is `127.0.0.1`; naming that "the phone" would be worse than having nothing. That is
exactly the case PROTOCOL.md v18 cites for why `addrs` exists.

**If the planner intended the chain to stop here, this was my error** — the code is additive and
easy to revert, and I would rather be told than have guessed silently.

## §2 — what was implemented

### 2.1 The generation counter — built first, before any consumer

Desktop, `Services/HotspotAnnounce.cs`:

```csharp
public static bool ShouldAccept(int incomingGen, int highestSeenGen) => incomingGen > highestSeenGen;
public const int NothingSeen = -1;
```

Phone, `service/AdbLinkRules.kt`: `AdbGeneration` — an `AtomicInteger` whose `next()` returns 1
first, so the first announcement of a process can never collide with a desktop seeding at 0.

`HotspotLinkService` re-checks the generation **under its gate** after taking it, because two
announcements can arrive back to back and the second must not be admitted against the value the
first already raised.

**`adb.down` is generation-gated too.** A stale `down` arriving after a newer `announce` would
otherwise tear down a link that had just been built correctly — the same failure the counter
exists to prevent, in the other direction.

### 2.2 Phone side: knowing your own adbd state — what shipped and what did not

| Method | Status | Notes |
|---|---|---|
| 1. System properties | **shipped in full** | `service.adb.tls.port` → `service.adb.tcp.port` → `persist.adb.tcp.port`, in that order, via reflection on the hidden `android.os.SystemProperties`. `-1`/`0`/unparseable are not ports. |
| 2. `NsdManager` self-discovery | **shipped in full** | Browses `_adb-tls-connect._tcp` then `_adb._tcp`, bounded to 400 ms total, and keeps only a service resolving to one of **this phone's own addresses**. |
| 3. Loopback scan | **shipped in its cheap half; the ephemeral sweep is DEFERRED** | See below. |

A miss at any step is "try the next method", never "adbd is down" — asserted directly in
`AdbLinkRulesTest`.

**`_adb-tls-pairing._tcp` maps to a `pairing` mode that is explicitly not connectable.** Pairing
being open means the desktop is *not* paired; announcing that port as connectable buys an
`unauthorized` and a retry loop that can never succeed.

**Why the ephemeral sweep is deferred, with the arithmetic.** §2.2 asks for `5555` plus the
ephemeral range. Android's ephemeral range is roughly 32768–61000 ≈ 28,000 ports. At the 200 ms
connect timeout the liveness gate uses, and bounded to a phone-safe 32 concurrent threads, a full
sweep is ≈ 28000 / 32 × 200 ms ≈ **175 seconds** — and even at an aggressive 50 ms timeout it is
≈ 44 s. That runs on the link-up path, on a phone, on battery. §2.2 says outright: *"If you cannot
make it cheap, ship methods 1–2 and report that method 3 is deferred; that is a better outcome
than a janky app."* So:

- **What shipped:** a single loopback connect to `5555` (~200 ms worst case), which covers the
  `adb tcpip 5555` case M13a assumes and the whole of this chain's hand-test.
- **What did not:** the ephemeral range sweep. The wireless-debugging (TLS) port is random and
  lands in that range, so **on a phone where methods 1 and 2 both miss and only wireless debugging
  is on, detection will fail.** Methods 1 and 2 are precisely the ones that normally cover that
  case, which is why deferring 3 is tolerable rather than fatal.
- **A cheaper route exists but is not usable:** `/proc/net/tcp` would name adbd's listening socket
  in ~1 ms, but since Android 10 an app can only see its own sockets there. Not attempted.

### 2.3 The liveness gate

`AdbAnnouncer.isAccepting(port)` — a real loopback `Socket.connect` with a 200 ms timeout, run for
**every** method's result before anything is announced. `verified: true` is set only from that
call's success. The gate is applied to method 3's guess and to methods 1 and 2's findings alike:
a port read from a system property is a claim, not a proof.

The desktop refuses `verified: false` in `HotspotAnnounce.RejectReason`, and that refusal is
negative-proof (b) below.

### 2.4 Desktop side

`Services/HotspotLinkService.cs`, attached from `AppShellViewModel` at launch (`adb.announce` is
unsolicited and arrives as soon as the phone's control connection comes up, so it cannot wait for
a page to be navigated to). Order inside `HandleAnnounceAsync`:

1. `HotspotAnnounce.Parse` → `HotspotAnnounce.RejectReason` (generation, then `verified`, then
   port sanity). Nothing is dialled before this returns null.
2. `HotspotAnnounce.ExpectedSerial` — identity settled **before** the dial.
3. `HotspotAddress.SelectEndpoint(PeerAddress, addrs, own interfaces)` — M13a's same-subnet
   filter, unchanged, still applied to `addrs`.
4. `HotspotConnector.ConnectAsync` — M13a's `adb disconnect` → `connect` → `get-state` →
   `get-serialno`, consumed for the first time here.
5. `HotspotAnnounce.ClassifyState`: `unauthorized` → log a pairing instruction and **do not
   retry**; `offline` → one more `ConnectAsync` (which disconnects first) and no more; `device` →
   accept.
6. `adb.ack {gen, ok, endpoint}` on every outcome, echoing the gen that was acted on.

`adb.arm` on the phone re-runs 2.2–2.3 and re-announces, which is the right answer whenever adbd
was already up and the desktop merely lost track of the port. Nothing arms anything — that is M13c.

## §5 — issues found in the task file and in PROTOCOL.md's v18 section

1. **PROTOCOL.md and M13b §2.6 disagree about an EQUAL `gen`.** PROTOCOL.md says the desktop
   "discards any message whose `gen` is **lower than** the highest seen", which admits a repeat.
   M13b §2.6 asks for "reject **equal-or-stale**". I implemented the stricter reading (strictly
   greater) because acting twice on one link event means a second `adb disconnect`/`connect` cycle
   against a link that is already up. **PROTOCOL.md's wording should be tightened to match, or the
   harness check inverted — they cannot both stand.** I did not edit PROTOCOL.md.

2. **`serial` cannot be a required field, and PROTOCOL.md's payload table implies it is.** An
   unprivileged Android app cannot read its own hardware serial on a modern release: `ro.serialno`
   is SELinux-guarded and `Build.SERIAL` has returned `"UNKNOWN"` since API 26. If the desktop
   required a non-empty `serial` to parse an announcement, **it would reject every real
   announcement.** Resolution: `serial` is optional on the wire, and the desktop verifies
   `get-serialno` against **the serial it is already paired with** (`HotspotAnnounce.ExpectedSerial`),
   treating the announced value as a cross-check that causes a refusal when it disagrees. This is
   strictly stronger than trusting the announcement, and it preserves "the ADB serial is the only
   stable identity". **PROTOCOL.md's v18 table should mark `serial` optional and say what it is
   checked against.**

3. **§1's gate versus §2.4's requirement** — see §1 above. The gate would have stopped the chain
   over a one-signature plumbing gap, and its stated rationale ("the announce protocol has nothing
   to attach to") is contradicted by the same spec's `addrs` fallback.

4. **§2.4 says "`adb disconnect` → `adb connect`" as if it were new work.** M13a already built
   exactly that sequence in `HotspotConnector`, and duplicating it here would have been the
   re-implementation failure GUIDE.md §4.1 warns about. M13b consumes M13a's connector instead.
   Not a defect in the file, but worth the planner knowing the wording reads as a fresh instruction.

5. **§2.4's "route to pairing" has no defined destination.** There is no existing entry point that
   opens the pairing flow from a background service. Implemented as an actionable log line plus a
   hard "do not retry"; see §4.

6. **Nothing in M13b says when the phone should announce.** §2 says "unsolicited, on every state
   change" but names no trigger. I chose two: the control handshake completing (which *is* the link
   event on a hotspot, and is when the desktop most needs the port), and `adb.arm`. **There is no
   connectivity-change listener** — a hotspot coming up while a control link is already established
   over some other transport will not trigger an announce until the next handshake or arm. Calling
   that out because it may matter to M13c's health loop.
