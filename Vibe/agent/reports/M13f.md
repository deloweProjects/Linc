## Part A — `TransportRank.Choose` (rank yields to liveness)

**Diagnosis, from the log `%LOCALAPPDATA%\Linc/logs/linc-2026-08-11.ndjson` (serial `<your-device-serial>`):**

- The supervisor DOES learn drops: "Connection dropped; will reconnect automatically." appears at
  00:20:35, 16:59:55, 17:09:06, 17:10:07, 17:12:15, 17:16:38. So **(a) is false as stated at the
  health mechanism level** — the current, live link is dropped and re-resolved correctly.
- Smoking gun for the USB pinning: **17:15:27** direct-TLS connect → **17:15:35** wireless
  `192.168.137.119:38787` connect → **17:15:47** "Connected to Pixel 7 (USB)". A fresh wireless
  link is pre-empted 12 s later by USB. Then the 17:35–17:39 period cycles the same way.
- So the cause is **(c) as the trigger + (b) as the mechanism**: the adb server's stale USB entry
  (the owner's own `192.168.137.119:38787 offline` line is precisely this shape) keeps the USB
  transport "present", and `TransportPriority` (USB=3 > Wireless=2 > DirectTls=1) with
  `ShouldEngage` auto-switching to a higher priority *while Connected* re-pins USB on every poll.
  The 3-consecutive-failure health gate only sees the *current link's* failures, never a USB
  dead-ghost, so USB re-wins each repoll — "the app sticks on USB long after the cable is gone."

**Fix.** New pure `Services/TransportRank.cs`: `TransportCandidate(Name, Rank, Answered)` +
`TransportRank.Choose(candidates) → string?`, returning the highest-ranked candidate that has
*answered*, null when none has. Wired into `ConnectionSupervisor.OnUsbDeviceSeen`'s paired branch:
when `Connected` and the current `Device` is non-null, the two candidates are USB and Wireless,
each answered only if the current link's RTT is non-null AND it is that transport. If
`Choose` does not pick USB, the stale USB report yields — no pre-empt. **The healthy live
wireless link keeps its rank; a USB entry that has not answered loses it.** A genuinely dead
link still fails the health gate → `OnLinkDropped()` → State becomes Searching → USB may re-engage,
so real failover is intact.

**Verification:** `hotspotsim` section asserts: live wireless beats stale un-answered USB; live
USB beats un-answered wireless; both answering → rank decides (USB); nothing answered → null;
empty list → null. **Negative proof (a):** reverted the `Answered` filter in production → the
"live wireless wins over stale USB" check **FAILED**; restored → green.

## Part B — real serial via `getprop`, not the endpoint

`adb get-serialno` over TCP returns the endpoint (`10.229.217.188:5555`), so the compare was
endpoint-against-endpoint and could never fail. `HotspotConnect.cs` now runs
`adb -s <endpoint> shell getprop ro.serialno` and compares that to `DeviceRegistry.PairedSerial`
through the new pure `HotspotAnnounce.VerifySerial(expected, reported)`; `get-state == device`
remains the liveness half. **Negative proof (b):** hollowed `VerifySerial` to `return true` →
the "wrong serial fails" check **FAILED**; restored → the newly-deleted wrong-serial case fails
and green.

## Part C — Direct-TLS advert re-enumerates on link change, virtual last

`TlsTransportService` advertised from a startup snapshot (`<vpn-address>` Radmin VPN,

## Part D — health loop endpoint

The malformed `ip:port:5555:5555` came from the connector unconditionally appending `:port` to an
`address` that already was `ip:port` (the health loop hands it the full endpoint). New pure
`Services/HotspotEndpoint.cs` (`.Build(address, port)`, `.IsEndpoint(value)`): passes an
already-valid endpoint through untouched, brackets bare IPv6, appends `:port` only otherwise.
`HotspotConnect.BuildEndpoint` delegates to it. **Negative proof (c):** reverted the pass-through
in production → the "already-an-endpoint passes through" check **FAILED**; restored → green.
