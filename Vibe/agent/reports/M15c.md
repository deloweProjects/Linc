## Part B — a pulled cable is now noticed in ~3-6 s
**B2.** `UsbWatcherService` gained `event Action<string>? UsbDeviceGone`; the existing 3 s poll now
also builds the set of usable USB serials and reports departures (`ReportDepartures`).
`ConnectionSupervisor.OnUsbDeviceGone` drops the link **only** when `State == Connected`, the live
transport is `AdbUsb`, and the vanished serial matches the live one — then calls the existing
`OnLinkDropped()` (which M15a already made trigger recovery). No other transport can be dropped by
absence from `adb devices`; a wireless link is not a USB row at all.

**B3 — guard chosen: two consecutive absences** (`UsbWatcherService.MissesToDeclareGone = 2`).
Why that over "one `offline` plus a confirm": B1 shows a real pull produces **no `offline` row at
all**, so an offline-based rule would almost never fire on this hardware, while a plain absence can
also be produced by an adb-server hiccup. Treating `offline` as absent folds both signals into the
one counter. A poll that throws (adb hiccup) counts *no* miss, so a dead adb server cannot kill a
healthy link either.

**B4 — timings.** Logged at `Warn` on the new path, in the same shape as M15a's detection log, so
the next cable pull is measurable from the log alone.
- New path: **best ~3 s, worst ~6 s** (one poll to notice + one to confirm; adb itself contributes
  ~0.3 s).
- Old path, unchanged and still the fallback for every other transport: 6-21 s (owner measured 19 s).
