## 3. The five rulings

### 3.1 Ruling 1.1 — `gen` filter is now `>=`. DONE.

`HotspotGeneration.ShouldAccept` in `Services/HotspotAnnounce.cs`:

```csharp
public static bool ShouldAccept(int incomingGen, int highestSeenGen) => incomingGen >= highestSeenGen;
```

The doc comment that argued for strictly-greater is replaced with the epoch reasoning and the
`adb tcpip 5555` case that motivates it. `HandleAnnounceAsync`'s "re-check under the gate" comment
was also corrected — it claimed a second same-gen announcement must not be admitted, which is now
the opposite of the rule.

**Harness checks that asserted the mistake were inverted, not deleted.** Per GUIDE.md §4.5 the flip
is made obvious rather than quiet: the block carries a comment saying M13d §1.1 inverts it
deliberately, and the opposite claim is asserted just as tightly.

- was `!ShouldAccept(2, 2)` "an EQUAL gen is rejected"
- now `ShouldAccept(2, 2)` "an EQUAL gen is **ACCEPTED** — gen marks the link epoch, and several
  messages legitimately share one"
- added `!ShouldAccept(4, 5)`, so "reject strictly lower" is checked one epoch back as well as far
  back — a `>=` that had been mistyped as `>= -1` would not survive it.

A whole new block covers the re-announce case by name, driving the real `RejectReason` gate: a
same-`gen` re-announce carrying a **new** port is admitted; the post-`adb tcpip 5555` re-announce at
5555 is admitted; a `tls → tcpip` mode change inside one epoch is admitted; a re-announce after a
failed `adb.ack` is admitted; the same announcement admitted **twice** proves last-write-wins rather
than first-only. The role-flip defence is re-asserted in the same block (`gen 6` against `7` is
still refused), and both `adb.down` directions are covered — a `down` from a previous epoch is still
discarded, one from the current epoch is now acted on.

`HotspotBackoff.ShouldReset` was deliberately **left** at strictly-greater. It answers a different
question — "is this a genuinely new link event?" — and a same-epoch re-announce is not one, so it
must not reopen the race or clear the backoff penalty.

### 3.4 Ruling 1.4 — `StartSpeculative()` now has a trigger. DONE.

**Where it is hooked.** `HotspotLinkService.Attach()` now also subscribes to
`ITlsTransportService.ControlArrived` — the control-connection-established event M13a widened to
carry `IPEndPoint?`. `ITlsTransportService` is a new constructor dependency of `HotspotLinkService`;
it is already an `AddSingleton` in `App.xaml.cs`, so no DI change was needed. The subscription lives
entirely in `HotspotLinkService`, and no transport-path file was touched.

The handler is deliberately inert about the stream:

```csharp
private void OnControlArrived(Stream stream, IPEndPoint? peer)
```

`ConnectionSupervisor` owns that stream and adopts or disposes it; reading or disposing it here
would silently kill the control connection. `hotspotsim` asserts by source text that the handler
body contains no `stream.` at all.

**What guards it.** A new pure static, `HotspotSpeculativeTrigger.ShouldFire(peer, myInterfaces,
gen, lastFiredGen, linkedEndpoint)` in `Services/HotspotHealth.cs`. Three conditions, all required:

1. **hotspot-shaped peer** — `HotspotAddress.IsHotspotShaped(peer, myInterfaces)`, also new, and
   deliberately expressed *through* `SelectEndpoint` rather than as a second copy of the
   same-subnet filter. It returns true only when the peer is the address `SelectEndpoint` would
   dial **in its own right**; a foreign peer that merely falls through to a gateway is rejected.
   That distinction is asserted directly in the harness.
2. **at most once per `gen`** — `gen <= lastFiredGen` refuses. The sentinel
   `HotspotSpeculativeTrigger.NeverFired` is `int.MinValue`, deliberately **below**
   `HotspotGeneration.NothingSeen`, because a control connection routinely arrives before any
   announcement and that very first attempt is the one worth racing. The harness asserts the
   ordering of the two sentinels as well as the behaviour.
3. **never over a verified link to that peer** — `HasVerifiedLinkTo(linkedEndpoint, peer)` compares
   on the **host only**. The port adbd answers on is never the control socket's source port, so a
   full `ip:port` comparison would never match and the guard would never fire. Bracketed IPv6
   endpoints are unbracketed before comparison.

`HotspotLinkService` records `_lastSpeculativeGen = HighestSeenGeneration` at the trigger site and
then fires.

**One unasked-for change, flagged as GUIDE.md §3 requires.** `StartSpeculative()` read
`connection.PeerAddress` for its guess. `ControlArrived` fires on the TLS accept thread *before*
`ConnectionSupervisor` has adopted the connection, and `PeerAddress` is only populated inside
`AdoptTlsConnectionAsync` — so at the moment of the trigger it is still `null`, `SelectEndpoint`
would have returned null or a gateway, and the branch would have silently done nothing. That is
precisely the "it is dead code" defect 1.4 exists to fix, reintroduced one layer down. So
`StartSpeculative()` now delegates to a private `StartSpeculative(string? peer)` and the trigger
passes the address the event carried. The public `IHotspotLinkService.StartSpeculative()` signature
is unchanged and still resolves `connection.PeerAddress` for any other caller. `hotspotsim` asserts
the handler does **not** read `connection.PeerAddress` before firing.

### 3.5 Ruling 1.5 — the `adb.arm` fallback. DONE. Sweep not built.

**The window: 5 seconds.** Reasoning, since the task asked me to pick and state it — the phone
announces as soon as it has proved the port with a loopback connect, which is a sub-second path, so
five seconds is comfortably longer than the healthy case and never fires on a phone that works. It
is short enough that a user has not yet concluded the feature is broken, and roughly an order of
magnitude below the 44–175 s sweep it stands in for. It is a named constant,
`HotspotArmFallback.Window`, and the harness bounds it (`> 0`, `<= 10 s`, `< 44 s`) rather than
pinning it, so a later re-tune inside the justified range does not produce a spurious failure.

**How it is armed.** Off the same `ControlArrived` event, and only when the peer is hotspot-shaped —
on any other link no announcement was ever due, so its absence says nothing. After `Window`,
`HotspotArmFallback.ShouldRequest(usableAnnouncementSeen, linkedEndpoint)` (pure) decides: it asks
only when **no** usable announcement has been seen **and** no link has come up some other way. Then
one plain-language line is logged and `RequestArmAsync(HotspotArmFallback.Prefer, ct)` sends
`adb.arm { gen, prefer: "tcpip" }`.

The line, verbatim from `HotspotArmFallback.Reason`:

> The phone hasn't said which port wireless debugging is listening on within 5 seconds, so Linc is
> asking it to use the standard port instead. Some phones don't expose that port to an app at all,
> and hunting for it takes minutes.

It names the situation, not the mechanism, and the harness asserts it contains no raw `adb` or
platform jargon (GUARDRAILS §Errors speak human).

The pending ask is cancelled the moment an announcement passes the gate and again the moment a race
is won — asking a phone to re-arm while a link is up would only tear it down. Its failure path logs
at Warn rather than swallowing (GUARDRAILS: "a silent catch is a bug factory").

**No UI was added. The sweep was not built** — and `hotspotsim` now asserts no `for (var port` and
no `Enumerable.Range(` ever appears in `HotspotLinkService.cs`, which is where it would creep in.

## 7. Things in this task file that were wrong, ambiguous, or need a follow-up decision

### 7.1 Ruling 1.1's stated purpose is not fully delivered by the change it asks for

This is the one that matters, and it needs the planner.

1.1's motivating case is: `adb tcpip 5555` rebinds adbd with no link event, the phone re-announces
the new port under the same `gen`, and strictly-greater discards it so "the whole promotion
optimisation silently never fires". Changing `ShouldAccept` fixes the **gate** — the message is now
admitted, which is what acceptance §3 asks me to prove, and I have.

But promotion only runs **after** a race has been won (`AttemptAsync`, "Won." branch). At that
moment `_race.IsSettled` is true, and `HotspotBackoff.ShouldReset` — correctly — does not reopen the
race for a same-epoch message. So the admitted re-announce reaches `AttemptAsync` and returns
immediately at `if (race.IsSettled) return;`. **The message gets in and then does nothing.**

The pre-link case *does* work: before any branch has won, a same-`gen` re-announce now dials
normally, which covers the `tls → tcpip` change and the re-announce-after-failed-`adb.ack` shapes.
It is specifically the post-promotion shape — the one 1.1 names first — that still stops one layer
in.

**I did not fix it.** 1.1 scoped the change to `ShouldAccept` and the harness, and reopening a
settled race for a same-epoch message is a real design decision about when a live link may be torn
down and redialled — not mine to make. It wants a ruling: either the race reopens when a same-`gen`
announcement carries a **different port** than the one currently linked, or promotion's own result
updates `LinkedEndpoint` directly, or the case is accepted as covered by the health loop's
disconnect/reconnect after `adb tcpip` kills the old connection.

### 7.2 The `prefer` field ruling 1.5 relies on is ignored by the phone

1.5's escape hatch is "`adb.arm` with `prefer: "tcpip"` asks the phone to arm legacy tcpip on a
*known* port". The desktop now sends exactly that. **The phone does not read `prefer`.**
`SocketServer.kt:600` handles `MessageType.ADB_ARM` as `onAdbArm("the PC asked for a re-arm")`,
which `CompanionService.kt:111` implements as `AdbArming.arm(this)` then
`AdbAnnouncer.announceNow(...)` — the payload is never parsed.

So in practice the fallback degrades to "re-arm and re-announce whatever adbd ends up on", which
helps only when arming happens to land on 5555. It does not currently guarantee the known port that
1.5's argument rests on.

I did not change the phone: 1.5 asked only for the desktop side, and a phone-side change to honour
`prefer` is a behaviour change to the arming path with no ruling behind it. **It wants one.**

### 7.3 Minor — the once-per-`gen` guard has no meaningful `gen` before the first announcement

Both guards in 1.4 are stated in terms of `gen`, but the trigger fires on the control connection,
which normally arrives *before* any announcement. `HighestSeenGeneration` is then still
`NothingSeen`, so "at most once per `gen`" degenerates to "at most once before the first
announcement" for the very first link-up. That is the correct behaviour and I implemented it
deliberately (sentinel below `NothingSeen`, asserted in the harness) — noting it only because the
ruling's wording implies the phone's counter is always available, and at the trigger point it is
not.

### 7.4 Acceptance §4 lists `hotspotprobe` among the harnesses that must be "green"

`hotspotprobe` is a read-only diagnostic, not a pass/fail harness — it exits 0 whatever it measures.
I ran it, it exited 0, and its output is in §5.3, but "green" is not a property it has. Read it as
"ran and printed a useful report", which it did.

## 9. Numbered manual test for the owner

Everything below needs hardware I was forbidden or unable to use. **Steps 1–4 are the ones that
matter — they are the first real test of §1.4's trigger and §1.5's fallback.** Nothing here needs a

**Prerequisites:** the Pixel 7 with the companion installed, and `Linc.Desktop` NOT running yet.

1. **Baseline, on the normal Wi-Fi.** Start `Linc.Desktop`. Wait for the phone to connect. Open
   **Logs** and look for the line beginning *"The phone connected from …, which is on this PC's own
   network"*. Note whether it appears, and what address it names.
   - **Expected:** it appears once, naming the phone's LAN address (192.168.1.x).
   - **If it appears more than once for one connection, the once-per-`gen` guard is not holding** —
     copy every occurrence with timestamps.

   connection. Look for *"The phone hasn't said which port wireless debugging is listening on within

   - If it does appear, note what the phone does in the next 10 s (does a *"Wireless debugging is up

     planner needs.

   <ip:port> via the speculative attempt"* vs *"…via the announced attempt"*, and copy the whole

   - **Please paste that line verbatim.** It is the first real measurement of the race and nobody
     has one yet.

4. **Restart, to exercise the once-per-`gen` guard across epochs.** Quit `Linc.Desktop` from the
   tray (it hides rather than exits — use the tray menu's Quit). Start it again. Repeat step 1.
