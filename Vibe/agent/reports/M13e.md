## 3. The three rulings

### 3.1 Ruling 1.1 — the redial decision. DONE.

**The rate-limit floor I chose: 3 seconds**, as `HotspotRedial.MinInterval`. Reasoning, since the
task asked me to pick and state it:

- **Twice `HotspotStageTimer.SuspiciouslySlow` (1.5 s).** A redial is a real teardown — `adb
  disconnect`, then a full connect / `get-state` / `get-serialno`. At 3 s one redial can never still
  be running when the next becomes allowed, so redials cannot overlap or queue.
- **Below `HotspotBackoff.PollInterval` (4 s)**, so the health loop stays the authority on a link
  that has genuinely died rather than being pre-empted by announcement-driven redials.
- A legitimate promotion happens **once per boot** and is never rate-limited in practice. Only a
  flapping phone ever meets this floor — which is exactly who it is for.

Both relationships are asserted in `hotspotsim` against the real constants, not restated as
literals, so re-tuning any of the three keeps them honest.

**The pure static**, in `Services/HotspotHealth.cs`:

```csharp
public static bool ShouldRedial(
    string? announcedEndpoint, string? currentEndpoint, bool verified, TimeSpan sinceLastRedial)
```

Rules, in order: `verified: false` never redials (tearing a working link down for an unproven port
is strictly worse than doing nothing); no announced endpoint, no redial; **no current endpoint, no
redial** — that is not a redial at all, it is the ordinary race, and answering true would
double-dial it; identical endpoints → **no redial, idempotently**; otherwise the floor decides.
Endpoint equality is trimmed and case-insensitive (`SameEndpoint`), so an IPv6 literal's case does
not read as a different endpoint.

**Where it is driven.** `HotspotLinkService.HandleAnnounceAsync`, inside the gate, once the address
is resolved. When `_race.IsSettled` — the exact condition M13d reported was swallowing the message —
it builds the announced endpoint with the production `HotspotConnector.BuildEndpoint(chosenAddress,
announcement.Port)` and asks `ShouldRedial`. On yes: log a plain-language line, reopen the race
(`_race = new HotspotRaceState()`), clear `LinkedEndpoint`, stop the health loop, then **outside the
gate** `adb disconnect` the OLD endpoint before `AttemptAsync` dials the new one. That disconnect is
not redundant with `ConnectAsync`'s own: `ConnectAsync` disconnects the endpoint it is *about to
dial*, which on a promotion is a different `ip:port`, so without this the dead entry stays cached and
adb keeps reporting a device that is gone. On no: ack `ok: true` with the endpoint already held, so
the phone stops re-announcing at a link that is already where it wants it.

One guard worth naming: the ack only fires when there really is an endpoint. A race can settle a
moment before `LinkedEndpoint` is assigned, and acking `ok: true` with an empty endpoint would tell
the phone a link exists that this side cannot name.

### 3.3 Ruling 1.3 — `syncsim`. Diagnosis: **(a)**. FIXED. `SyncEngine` untouched.

**It is (a): a harness ordering assumption. It is not a regression in `SyncEngine`'s newest-wins
logic.** The engine's decision was correct on the world it was shown; the harness showed it a
half-built one.

**Evidence.** I first characterised it: **four of five runs failed**, and all three checks in
`newest-wins phone -> PC` failed together — including `phone side unchanged`, which means the
*phone's* copy had changed. That already ruled out a pull-side comparison bug. I then exposed the
real engine's log through the harness and printed it on failure. For a failing run it is **one
line**:

```
  FAIL  newest-wins phone -> PC
          newer phone copy won
          stable on the next pass
          phone side unchanged
          -- engine log (16 passes listed the folders):
             Info: Synced conflict.txt to the phone
```

**A push, PC → phone. No pull ever happened.**

The mechanism: `SyncEngine`'s constructor calls `Reconfigure()`, which `Kick()`s a pass onto the
thread pool immediately. `Harness`'s constructor built the engine, and *then* each scenario body
wrote its fixture files — so that pass ran concurrently with the setup it was meant to test. In the
window between `WritePc` and `WritePhone` the engine saw a PC file and an empty phone folder,
correctly decided to push, and wrote the **old** PC copy over the phone's newer one. The seen-state
then recorded both sides in sync at the PC's mtime, so every later pass saw nothing changed and
never pulled. All three assertions fail from that one race.

Two details that seal it as the harness's fault, not the engine's:

1. The scenarios **backdate every fixture's mtime** (`minutesAgo: 10`, `30`). That defeats
   `SyncEngine.SettleSeconds` — the 2-second rule that in production stops the engine acting on a
   file still being written. The harness disabled the protection and then raced it.
2. Nothing about the engine's newest-wins arithmetic is involved. Given what it listed, push was the
   right answer.

**The task's prime suspect was wrong, and worth saying so.** §1.3 nominates filesystem mtime
granularity — "two files written inside the same timestamp tick are not ordered". That is not it:
the two fixtures' mtimes are explicitly set **29 minutes apart**. The race is in *when the engine
starts*, not in the resolution of the clock it reads.

**The fix, in `tools/syncsim/Program.cs`.** The engine is no longer constructed by `Harness`'s
constructor; it is created on the **first `Reconcile()`**, by which time the fixtures are on disk.
That is an ordering guarantee, not a sleep — M4b's lesson from `cleanroomsim`'s fixed 5 s wait. A
long comment at the old construction site records the whole diagnosis so the next session does not
undo it.

The guarantee is **asserted, not assumed**. The first `Reconcile()` checks that no engine had been
built and that no pass had listed the folders (`FakePhoneFiles.ListCount`, new). The flag driving
that check is deliberately separate from `_engine` — keying it off "`_engine is null`" would make the
check silently skip itself the moment someone put construction back in the constructor, which is
precisely the change it exists to catch. That is negative proof (b), and it fails in **all 12
scenarios** when reverted.

I also kept the engine-log printing: a failure now says *what the engine did*, not only which claim
broke. The absence of that is what let this sit as "a known flake" through two milestones.

## 7. Things in this task file that were wrong, or that need a follow-up decision

### 7.1 The announced port was never dialled — fixed, and flagged as unasked-for

`IHotspotConnector.ConnectAsync(string address, string? expectedSerial, CancellationToken ct)` built
its endpoint as `BuildEndpoint(address)`, which defaults to `AdbTcpPort` = 5555. `AttemptAsync`
received the announced `port` and used it **only** to decide whether to promote — it never reached
the dial. So since M13b, **every `adb.announce` was dialled at 5555 whatever port it named**, and the
announce path could only ever succeed against a phone already on the fixed port.

**This blocked 1.1 directly.** `ShouldRedial` compares an announced endpoint against the connected
one; if the dial is hardcoded to 5555, the two can never differ for a port change, and the rule would
have been a decision the code could not honour. So per GUIDE.md §3 I made the smallest change that
lets the task be completed correctly, and I am flagging it rather than burying it:

- `ConnectAsync` gained a trailing `int port = HotspotConnector.AdbTcpPort` and builds
  `BuildEndpoint(address, port)`.
- `AttemptAsync` passes its existing `port` argument through, on both the first attempt and the
  `offline` retry.
- `hotspotsim` asserts the pass-through by source text, so it cannot silently regress.

The default keeps every other caller compiling and behaving exactly as before.

### 7.2 The health loop passes an endpoint where an address is expected — NOT fixed

`HotspotLinkService.HealthLoopAsync` calls:

```csharp
var result = await connector.ConnectAsync(endpoint, expectedSerial, ct);
```

`endpoint` here is `result.Endpoint`, i.e. `"192.168.43.1:5555"`. But `ConnectAsync`'s first
parameter is an **address**, and it calls `BuildEndpoint` on it. `BuildEndpoint` tries
`IPAddress.TryParse("192.168.43.1:5555")`, which fails, and returns the string with a port appended:

```
192.168.43.1:5555:5555
```

Every reconnect the health loop attempts is therefore aimed at a malformed endpoint and cannot
succeed. `DisconnectAsync` and `GetStateAsync` in the same loop are fine — they genuinely take an
endpoint.

**I did not fix it.** It is M13c code, it is not needed for any of M13e's three rulings, and GUIDE.md

## 9. Numbered manual test for the owner

Everything below needs hardware I was forbidden or unable to use. **Steps 3–5 are new to this
milestone and are the first real test of the promotion path.** Nothing needs a rebuild; the Debug
build and the Release publish are both current.

**Prerequisites:** the Pixel 7 with the companion installed, `Linc.Desktop` not yet running.

1. **Baseline on the normal Wi-Fi.** Start `Linc.Desktop`, wait for the phone to connect, open
   **Logs**. Copy any line containing *"Wireless debugging is up at"* — it carries the per-stage
   timings and says which branch won. Nobody has one of these yet.

2. **The phone's new `adb.arm` line.** On the **phone's** Logs screen, look for *"The PC asked to
   re-arm wireless debugging"*. On a healthy phone it should **not** appear — the desktop only asks
   after 5 s of silence. If it does appear, note whether it says *"it would prefer 'tcpip'"*.

3. **The promotion redial (the new path).** Watch the desktop Logs for
   *"The phone moved wireless debugging from `<A>` to `<B>`; reconnecting there."*
   - **Expected** if the phone first announces an ephemeral port: one such line, `<B>` ending
     `:5555`, followed by a *"Wireless debugging is up at …:5555"*.
   - **Please paste both lines.** This is the case M13d and M13e exist for and it has never run.

4. **Idempotence.** Keep watching for ~60 s after step 3. There must be **no** repeated
   *"moved wireless debugging"* line and no repeated connect. If you see the pair repeating in a
   loop, that is the reconnect storm the 3-second floor is meant to prevent — copy the timestamps.

5. **The health loop after a promotion.** After step 3 succeeds, leave it for a minute and look for
   *"The wireless debugging link to … isn't answering"*. **If that line appears repeatedly while the
   phone is plainly fine, that is §7.2** — the malformed `ip:port:port` reconnect. Copy it; it is
   the evidence that finding needs.

6. **The hotspot, phone-hosted.** Turn the phone's hotspot on, join this PC to it, then from
   `…\yellow\Linc\`: `dotnet run --project tools/hotspotprobe`. **Paste the whole output** —
   especially §2's PUBLIC-interface warning and §5's reachability table.

7. **The hotspot, PC-hosted.** Windows Mobile Hotspot on, phone joins it, run `hotspotprobe` again
   and paste. For both 6 and 7: is *Wireless debugging* still togglable on the phone, and what does
   `adb devices` say?

**Do NOT** run `devicesim` while `Linc.Desktop` is running, and never pipe it into anything that can
exit early — it deletes and restores the real `settings.json` and must run to completion.
